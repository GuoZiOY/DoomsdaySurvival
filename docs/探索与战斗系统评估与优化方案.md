## 三、★ 一条被证伪的高危推测（方法论记录）

审计报告 **01 #23** 曾给出 **🔴🔴** 结论：

> 四个离线验证器 target `net10.0`，游戏是 Unity 6（.NET Standard 2.1 面）→ `System.Random` 带种子的算法不同 → **"验证过的布局"和"游戏里的布局"不是同一套**。

**如果成立，本项目所有"绿灯"都要作废**。于是当场做了判定实验（同一批种子，两边各取前 6 个 `Next(100)`）：

| 种子 | .NET Framework 4.x（Windows PowerShell 5.1） | net10.0（CLR 10.0.2） | |
|---|---|---|---|
| 1 | 24,11,46,77,65,43 | 24,11,46,77,65,43 | ✅ |
| 12345 | 6,7,77,51,79,82 | 6,7,77,51,79,82 | ✅ |
| 20260913 | 56,90,63,20,50,99 | 56,90,63,20,50,99 | ✅ |
| 2147483646 | 20,52,6,34,75,68 | 20,52,6,34,75,68 | ✅ |

**逐位一致** → `new Random(seed)` 在 .NET 6+ **刻意保留了旧的 Knuth 算法**（变的是无参 `Random()`），而 Mono/Unity 用的正是这一族。
**结论：#23 不成立**，离线验证与游戏**是同一套布局**。级别由 🔴🔴 降为 🟡（保险项）。

两条如实补充：
1. 用 .NET Framework 代表 Mono 是**推理**，没在 Unity 里真跑 —— 要盖章只需在编辑器里 5 行：`new Random(12345).Next(100)` 打 6 个值对表。
2. 微软文档仍写"跨大版本不保证一致"，所以报告 01 的"给随机源上锁（换成仓库自带的可播种实现）"**仍值得做**，只是不紧急。

**而这一轮出现了两次"自己抓自己"，都值得记进纪律**：
- 本文作者的对照脚本第一版**自己写错了**（Int32 溢出 + 参考实现有偏），第一次跑出来的是"✗ 不一致" —— 差点把一个假警报升级成头号问题，是**换用两个真实运行时对拍**才纠正的。
- 本文作者在 v51 刀10 往文档里写过一句「`当前节点` **已删**」，**纯属没核实就写**，被 `docs/评估/06` 的交叉核对抓出来（该字段有 11 处引用，且是**存档"是否已开局"的守卫**，删了会存出坏档）。已更正（提交 `516eda1`）。

> **教训（建议进 `工作移交报告` §六）**：**"已删 / 已改 / 已验证 / 不一致" 这类断言，和代码断言一样必须实证**——包括写给未来自己看的文档。本项目有 6 个工具、40 条纪律，却**没有任何机制守"文档里的断言"**（见 §四 档 2 的 `Tools/文档核对.ps1`）。

## 五、做得好的地方（不夸不行，但要说清好在哪）

1. **生成层的验证纪律是真的**：4 个逐种子验证器 + 数据引用核对，断言的是**有意义的不变量**（连通分量、门口可达、撤回数必须为 0、确定性指纹），而不是"跑通不报错"。
2. **本会话新加的 3 个纯规则文件证明了路线可行**：`搜索规则` / `网格可见性` / `迷雾位图` 都是"抽出来就能逐点断言"（迷雾位图那条还专门验了四角+最后一格）。
3. **`格子探索服务` 的基类不变量声明**（文件头 11-14 / 89-94 / 425-427 行）把"什么是派生类的责任"写清楚了，实测确实没有"该下沉未下沉"的逻辑（02 §四）。
4. **已知并系统性防过的问题只漏了一个**：`档案` 用闭包快照这件事，`BattleService.cs:12` 的注释直接写明"不能缓存旧引用"——说明团队知道这个坑，只是 `搜索服务` 漏了（B1）。
5. **`面板管理器` 的零接线兜底 + 明确警告**（"已自动建一个，要能美观请手动搭配"）是"静默失败"的反面教材。
6. **文档里的"为什么这么写"**：过期的部分是少数（见 F4），大量注释解释了取舍理由（例如"敌人在记忆层里不许画"、"楼梯边不能和入口边同边"）。
7. **数据与文档的一致性经得起抽查**：12 项条目数全对、25 个硬编码标识全部存在、`文件:行号` 0 越界 —— 这在个人项目里相当少见。
