## 二、总体印象

### 2.1 分层是干净的，问题几乎全在"生命期"

基类 `格子探索服务` 的分层**真的分开了**：它只认"格子 / 令牌 / 路径 / 视野 / 迷雾 / 时间 / 网格同步"，
门锁、搜索、钥匙、楼层、临时建筑这些**内容语义**全部留在派生类里（`格子探索服务.cs:11-14` 的注释是这类
"不变量声明"写得最清楚的几处之一）。遭遇与战斗这一段从房间层上移到基类（`格子探索服务.cs:425-427`）
之后，三层共享同一套流程、只填"胜负节点 / 棋盘 / 日志前缀 / 先手 / 胜利之后 / 收尾之后"六个语义钩子
（`格子探索服务.cs:436-445`），这是很干净的模板方法用法。**我逐行点过基类，没有找到"该下沉却没下沉"
的派生专有逻辑**（任务问题 2 的答案：没有）。

风险不在分层，而在**生命期**：三层各自带一堆"本趟 / 每次进门 / 永久"的表，生命周期靠注释约定，
没有任何机制强制；`清战局()` / `离开前()` / `装好房间()` / `进入X()` 四个入口都要各自记得清什么，
已经能看出重复（`最近尸体容器` 6 个清点、5 行 × 3 份的样板清态）与漏项
（`遭遇前格`、`本次战斗来自本层` 跨世界不复位）。

### 2.2 三条已知线索的核实结论（任务问题 5/6 的直接回答）

- **`时间变化事件` 当每帧 tick 用：属实，且是本次最确凿的性能问题**（F7）。
  链路 `战斗沙盒面板.Update:267 → BattleService.推进战斗 → :163 发布 → 格子探索服务:405-409 无条件刷新视野`
  逐环可查。60 秒战斗 ≈ **3,600 次** `new HashSet<int>(225)` + 约 **162 万次**哈希写入 +
  3,600 次字符串分配 + 3,600 次 TMP 富文本重解析。修法极短（删 1 行 + 挪 1 个调用）。
- **`搜索服务` 用过期档案：属实**（F6）。`GameBootstrap.cs:70-72` 只在装配时接一次，
  `搜索服务.cs:74` 的闭包捕获了那次传进来的档案实例，而 `PlayerService.cs:33/155` 会**整体替换**档案实例，
  `PlayerService.cs:71-72` 只重接了 `容器服务`。**全仓库 6 处 `档案` 持有者里，只有 `搜索服务` 与
  `容器服务` 是闭包快照**，其余（`BattleService:12`、`QuestService:8`、`技能服务:11`、`天赋服务:12`、
  `格子探索服务:63`、`网格面板基类:33`）都是"动态取当前档案"的属性 —— 而 `BattleService.cs:12` 的注释
  直接写明了原因。所以这是一处**项目已知并系统性防过、但漏了一个服务**的问题。
- 派生类重复订阅基类事件：**已修且留了证**（`房间探索服务.cs:63-65` 的注释 +
  `docs/工作移交报告.md` §六 #31）。本次复查三个派生类，**没有第二处重复订阅**。

### 2.3 与项目既有纪律的交叉核对（发现 2 条"违反自定纪律"）

读了 `docs/工作移交报告.md` §六（40 条坑与约定）之后，本次发现里有 2 条是**明文违反项目自己写下的纪律**：

| 纪律 | 出处 | 本次发现 |
|---|---|---|
| "任何推进时间必须走 `世界时间管理器`（**禁止直接改 `游戏分钟数`**）" | `docs/工作移交报告.md:587`（§六 #4） | **F8**：`BattleService.cs:161`、`生存管理器.cs:74`、`工作台制作服务.cs:254/301` 共 4 处直接改 |
| "服务只发意图、UI 负责切面板……服务里直接调 `面板管理器` 会同时破坏分层与返回判断" | `docs/工作移交报告.md:634-636`（§六 #37） | **F13**：`房间探索服务.cs:637` 直接调 `搜索面板.打开搜索(...)`（唯一一处，且无注释说明为何例外） |

另外两条**被纪律确认是"设计"而不是 bug**，我已从问题清单里划掉：
- "大世界不另存位置（读档 = 从安全屋出发）"是 **v51 定版口径**（`docs/工作移交报告.md:405-407` +
  §五 #12），所以 F9 里"位置不存档"降级为**注释已记录的已知状态**，不是漏项。
- 永久迷雾的位图对称性断言**确实存在**（`Tools/大世界验证/Program.cs:473-502`，含三种尺寸 × 四角 +
  最后一格 + 界外格码丢弃 + 坏档不崩），所以 `迷雾位图.cs:14-16` 的注释**没有说谎** ——
  我在 F16 初稿里怀疑它"注释与实现不符"，**已核实并撤回**。

### 2.4 一句话总结

**架构是好的，纪律是有的，注解是罕见的详实；风险集中在"没有机制强制的生命期"和
"服务层的依赖绑定时机"这两类问题上，两者都可以用很小的代码改动（合计约 60 行）从"靠约定"变成"靠代码"。**

## 四、发现清单

### F1 🟡 `进入房间()` 无条件 `楼层缓存.Clear()`，楼里换层的正确性靠调用顺序

- **现在怎么做**：`进入房间()`（`房间探索服务.cs:120-154`）第 129 行 `楼层缓存.Clear()`、第 127-128 行把
  `当前建筑 = null; 当前层 = -1;`。而楼内换层走的是 `切到房间()`（`:261-289`），它**不清**缓存 —— 正确。
- **问题**：`进入房间()` 是"单间模式"入口，它清缓存是对的；但它同时也是 `推门出去()`（`:454`）和
  区域/大世界 `进楼()` 的入口。也就是说"清缓存"这一行为绑定在"模板对不对"的校验之后、`当前建筑` 重置之前，
  没有 `在建筑里` 的守卫。目前所有调用方都在"确实不在楼里"的时候调它，所以是**正确的**；
