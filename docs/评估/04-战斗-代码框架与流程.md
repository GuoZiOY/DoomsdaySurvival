## 二、总体印象

1. **`BattleService` 是一条真正跑通了的即时制战斗流水线，不是玩具**：世界时间→行动条→意图锁读条→满条执行→打断/眩晕→伤害管线→尸体搜刮→三层回派，全链路闭合，v44/v45/v46 三代迭代的取舍都写在注释里且与代码一致。同类项目里"即时制 + 意图承诺 + 秒制冷却 + 节点轨道"能被一个人写到这个完整度，属少见。
2. **但它同时是**这个仓库里最大的一个上帝类：1326 行同时容纳**状态机 / 轨道几何 / AI / 数值 / 资源（弹药-消耗物-耐久）/ 掉落与尸体 / 时间推进 / 消息文本 / 跨服务查询**九类职责。它不是"长得像"，是**确实**在九个方向上都有独立演化压力。
3. **最要命的不是行数，是三条边界被穿透**：① 时钟不是自己的（`推进战斗` 由 UI 面板的 `Update` 每帧喂 `Time.deltaTime`）；② 领域层不纯（存档/容器/词缀/任务/天赋/音效全从流程里直接调）；③ 结算与表现耦合（结算路径里直接 `发消息` 拼富文本、直接 `音效管理器.实例?.播放失败()`）。
4. **数值公式其实集中得不错**（唯一伤害权威 `造成伤害`），但**没有一处是纯函数**：命中/暴击/耐久/文本全在同一函数里，全部依赖 `UnityEngine.Random`（全局静态、不可播种）→ **离线验数值这条路现在是 0**。仓库已有 5 个离线验证器（区域/大世界/建筑/户型/房间），**没有战斗验证器**，是一条空白。
5. **数据驱动被"数据缺口"而非"硬编码"破坏**：`enemies.json` 9 只敌人**一只都没写 `行动表`** → AI 技能分支（`选定敌人意图` 的技能意图、读条大招、被撞断）**从未被执行过**；技能库里 21 个技能的敌人侧技能（抓挠/扑咬/精准箭/重锤砸击）全是死数据。代码写得对，**数据没配上，等于这条功能没验收**。
6. **最大的流程漏洞是"战斗引擎挂在 UI 面板的激活状态上"**：`战鬦沙盒面板.Update` 是唯一的 `推进战斗` 调用点，而 `面板基类.隐藏面板` 就是 `SetActive(false)`；同时 F1 打开持有面板**没有战斗拦截** → **战斗中按 F1，整个战斗时间冻结**。这是 🔴，且修起来只需要一行守卫。

## 四、战斗状态机（文字版迁移图）

### 4.1 阶段与字段

`BattleService` **没有显式状态枚举**，实际阶段由 4 个字段组合表达：

### 4.3 四个"非法中间态"及其现状

| # | 中间态 | 怎么发生 | 现状 |
|---|---|---|---|
| 1 | **`战斗中=false` 但面板仍在最上层** | `结束战斗` 先清 `战斗中`（1238），`战斗结束事件` 让面板"显示结算"（247）。格子层战斗随后在**同一调用栈内**切走面板（1256→`战斗收尾之后`），但**剧情战斗不切**（结果节点不以 `__` 开头）→ 面板自己什么都不做 | 🟡 靠"玩家点[继续]"（面板 44）或剧情流程推进。`战斗中=false` 期间攻击/移动/切换按钮仍可点，但每个入口都自查 `战斗中`（481/502/651/660/729）→ **不会坏，但完全依赖各家自查**（没有集中按钮屏蔽） |

| 3 | **重复 `返回()`** | `返回` 有幂等（1292-1294：先读后清），但**分派之前就清了** | 🔴 若 `战斗胜利()` 抛异常/早退（如 `当前世界==null` 时它在 489 直接 return，**结果节点已清**）→ 战斗永久卡在"已结束"，面板不再切回，尸体与实体不落地。**幂等锁位置错了**（应先分派成功再清，或 try/finally + 失败标记） |
| 4 | **结算中途重入 `开始战斗`** | 无守卫。`结束战斗` 发 `战斗结束事件` 时，订阅者链路里任何一处（奖励/剧情钩子/测试面板）再调 `开始战斗` → `结果节点` 被新战斗覆盖，旧结果永久丢失 | 🟡 当前无订阅者这么做（已核 `战斗结束事件` 全部 5 个订阅点：格子探索服务 75 / 战斗沙盒面板 37 / 侧边栏 33 / HUD 43 / 自动存档器 23），但**没有一行防御**。加 `if (战斗中) return;` 即可 |

### 4.4 状态机的真正问题（一句话）

**引擎状态（`战斗中`）与"待回派结果"（`结果节点`）耦合在同一个类里，而回派动作又内联在结算路径中**——正确写法是 `结束战斗` 只负责"算出结果并落状态"，把 `返回()` 交给驱动方（面板/探索层）在下一帧或结算完成后调用。现在的写法让"结算未完成"与"层已切换"可以同时为真。

## 六、做得好的地方

> 本节逐条给出"为什么这不是问题"，包括看起来怪但有注释/文档解释的刻意取舍。

1. **`指定敌人` 参数解决了"一个标识变多只"的历史 bug，且写法干净。**
   `开始战斗(… IList<(string 定义标识, string 实例标识)> 指定敌人 = null)`（`BattleService.cs:51-52`）用"几项就打几只、不再乘 `敌人组.数量`"（47-50 注释）一次性堵住了房间层"显示 2 只打起来 4 只"的老坑（移交报告 262 记录了完整经过）。同时 `实例标识` 写进战斗单位（86 / 99），落实了"一个标识 = 一个单位"铁律。**这不是补丁，是接口设计的修正**——可选参数 + 兼容旧语义（不传 = 按组展开）让三层调用方零改动。

2. **"全项目唯一伤害公式权威"这句注释是真的。**
   `造成伤害`（1107-1154）与 `造成固定伤害`（1157-1165）是仅有的两处改血入口（另有 `轮次结算` 的毒伤走 `受到伤害` 直调，204/217——**这是唯一例外**，但它绕过命中/减伤是"真实伤害"语义的合理表达）。判断顺序（无敌→命中→真实伤→暴击→防御→抗性→姿态）在注释里写清（1109-1110）、在代码里顺序一致。对比同规模项目"伤害公式散在 5 个地方"，这是**明确的好**。

3. **意图承诺制的"落空回退"做了双保险，不会白费一轮。**
   `执行技能意图`（335-344）在就绪/目标校验失败时 `自动移动(施法者)` 而不是空过；`单位自动行动`（297-303）在"蓄力被取消但意图还是技能"时**再兜底一次**改判为攻击/移动。`docs/技能系统设计.md:28` 明确写了这条设计（"落空处理 → 取消预约并落回本次行动位的自动行动（不白耗一轮）"），**代码与设计文档一致**。这是即时制手感的关键，做对了。

4. **打断/眩晕的三级语义清晰且双向对称。**
   `中断读条`（1051-1061）一条函数服务三个来源：受控冻结（173）、冲撞命中（1038-1042）、技能眩晕（`施加眩晕` 1064-1070 先断读条再冻结）；`眩晕剩余秒` 走**秒制**（战斗单位.cs:113-115，刷新取更长）而不是轮制，配合"冷却也改现实秒"（181-183）是自洽的一套时间语义。移交报告 217 记录了这次迭代的理由。**"先断读条 + 冻结期间不清条"（172-173）导致眩晕结束后立即出手——这是刻意的**（注释 169 与 113 都写了"读条冻结"，即保留进度），不是 bug。

5. **节点式轨道几何只有约 40 行，规则完备无死角。**
   `自动移动`（375-409）：玩家三种运动模式（378-384）、敌人三种移动 AI（389-401）、"前方节点被敌方占据 → 停相邻"（406-407）、出界停（404-405）；`可攻击目标` 用节点差 ≤ 攻击距离（347-358）且**明确注释"轨道无障碍，无需视线"**（346），与 v45"去障碍物"的决策（移交报告 199）一致。`推挤级联`（1025-1047）把"冲撞把挡路敌人顶退并连带撞断其读条"实现成一个 23 行的函数，**没有为它引入任何新的数据结构**。这是"用最少的结构表达最多规则"的好例子。

6. **"一场遭遇 = 一个敌人"在战斗侧和探索侧都被真正遵守。**
   战斗侧见第 1 条；探索侧 `检查遭遇`（格子探索服务.cs:448-458）只取正交相邻的一个敌人、`开始遭遇`（460-474）只把**这一个**标识交给战斗（471）、`战斗胜利`（487-523）只移除**这一只**并在原位留尸体（493-514）。移交报告 261-262 记录了"打死不留尸体"与"一只变多只"两个修复的完整推理。**铁律不是文档口号，是代码里能指认的四处。**

7. **"打赢必定留一具可搜尸体"是硬保证，且空尸体是被允许的。**
   两道闸门：`搜索服务.注册尸体容器` 显式允许 `物品 == null`（搜索服务.cs:114-119、134-135 注释"不给'没掉落就什么都不留'留后门"），`格子探索服务.战斗胜利` 在战斗没产出时自己登记 `搜索时间 0.5f` 的空尸体（496-497）。移交报告 260 完整记录了这个修复。**这是"从玩家行为出发"而不是"从数据出发"的设计**——末日搜刮玩法里"尸体可搜"是体验前提，不是掉落率的函数。

8. **三层共用的遭遇流程，派生只填语义，且"不许重复订阅"的坑写进了注释。**
   `格子探索服务` 的 7 个虚钩子（436-445）+ 5 个流程方法（448-541）让房间/区域/大世界三层共用一套遭遇逻辑；`房间探索服务.cs:63-64` 有一行明确注释"**不要再订阅 战斗结束事件** —— 基类已经订阅了，派生再订一次会**触发两遍**"。移交报告 618 把这个坑列为"开发注意事项"第 31 条。文档、注释、代码三处闭环。

9. **`返回()` 的幂等设计（先读后清）本身是对的意图。**
   1292-1294 的 `string 节点 = 结果节点; if (空) return; 结果节点 = "";` 明确为了防"自动返回 + 面板[继续] 两边都调"（1289 注释）。**只是清的时机早了**（见 #3）——不该因为时机错就否定这个幂等意图本身。

10. **"战斗中不结算生存"是有意取舍，注释与文档双重说明。**
    `推进战斗` 的注释（151-152）写明"战斗中不结算生存（饱食/水分/伤病 暂停——战斗冲突中不吃不喝也不扣）"；`世界时间管理器.驱动`（399-406）的注释写明"战斗中：时间由战斗沙盒推进战斗() 统一推进…挂机驱动暂停，**防双时钟**"；移交报告 198 记录了 v45 的这条决策。**这是明确的产品决策，不是遗漏**——问题只在"实现方式用'顶基准'来表达"（见 #11）和"没有终止兜底"（见 #11 第 ⑤ 点）。

11. **`推进战斗` 的每帧入口做了最必要的短路。**
    `if (!战斗中 || 现实秒 <= 0f) return;`（155）+ `处理满条行动` 里每个函数都自查 `战斗中`（291 / 228）→ 结算过程中途结束不会继续跑行动。这一点保证了 #2（结算内联切面板）"不会立刻崩"，属于**有意或无意的正确防御**。

12. **注释质量整体很高，历史决策可追溯。**
    具体例：`累计金币` 为何删（34）、`命中加成` 为何删（战斗单位.cs:223）、时间速率为何改 virtual（格子探索服务.cs:19-21）、六节点分派的来历（1295-1296）、迷雾记忆键为何带种子（格子探索服务.cs:120-123）。**这些注释让"看着怪"的地方都能自证**，是本次评估能给出确定结论的前提。

### 第 2 件：把结算与回派拆开（修 🔴 #2 + #3 + #5，约 45 行）

**为什么优先**：这三条是**同一处代码的三种错法**，一起改一次测试即可：
- `结束战斗` 内联 `返回()`（1256）→ 结算中途切层；

**动哪个文件**：`Assets/Scripts/Services/BattleService.cs` 的 1236-1304（`结束战斗`/`结算失败惩罚`/`结算回写`/`返回`）+ `结算单个敌人:1197-1199`。
