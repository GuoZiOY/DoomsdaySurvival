## 二、总体印象

**一句话：这是一份"注释质量远高于代码质量"的工程 —— 设计纪律、踩坑溯源、数学论证都写得极好，但正是这些注释暴露出几处结构性重复，和一条"数据/命名一改就静默失效"的通道。**

**做得最出色的三件事**（详细见 §四）：

1. **"踩坑记忆"被写进代码**，不是装饰性注释：`大世界生成器.cs:304-313` 自己写了"这一课在 v51 刀2 与 刀6 各栽过一次"；`网格数据.cs:57-62` 写清了"曾经按阵营判玩家，靠走运没炸，v52 改成按类型判"。这类注释是**防止后来者好心办坏事**的最强手段。
2. **`约束摆放` 是一个真正解耦的摆放引擎**（`约束摆放.cs:20-24`：只认宽/高 + `Func` 建实体回调），并且**明确声明了可靠性边界**（`:9-11`：引擎只保证"尝试时合法"，不保证最终不变量）。这种"明说我不负责什么"的注释极少见。
3. **确定性设计成体系**：`确定性随机.派生(种子, "用途字符串")` 给每类内容一条独立子流（`房间生成器.cs:74/126/284/338/527`、`区域生成器.cs:117/205/326/366`、`大世界生成器.cs:236/274/400`）。**加一类新内容不会挪动已有内容的随机序列** —— 这是有前瞻性的正确做法。

**最该警惕的两件事**：

1. 🔴 **`DataService` 的 `获取标识` 用反射按字符串取 `标识` 字段**（`DataService.cs:150-154`），取不到就静默丢整项（`:145`，无任何报错）。这是一个"编译期契约 → 运行期字符串匹配"的降级：将来任何一个 DTO 漏写/改名 `标识`，那张表会**整表消失且不报错**。
2. 🔴 **两条"数据写歪就静默错行为"的通道**：`大世界生成器.cs:241` 的 `Math.Max(1, 项.数量)` 会把"写 0 想关掉的敌人"强行撒 1 只（与 `区域生成器.cs:331` 的 `Max(0,...)` 相反，#13）；`视野规则.cs:46-51` 对 `夜晚起` 不做保护，数据漏填 → `判时段` 恒为夜晚（#21）。

**最该警惕的结构性重复（不致命但会持续放血）**："占格物不碰门口四邻"这条不变量有 **5 处实现**（`约束摆放.cs:203`、`区域生成器.cs:400`、`大世界生成器.cs:314`、`:443`，以及 `约束摆放.cs:158` 的隐式版本），**三套生成期写法 + 两套验证期写法，而 `DataService` 完全不查**（#8 / #29）。作者自己在 `大世界生成器.cs:304-313` 记录了这条规则**栽过两次**（v51 刀2 与 刀6）—— 说明它还没有收敛成一个可复用的谓词，第 6 次踩坑只是时间问题。

> **一次自我更正（重要）**：我最初把"验证器 net10 vs 游戏 Unity 的 `System.Random` 序列可能不同"列为最高危项（#14/#23）。**实测推翻了它** —— 我用 Unity 自带的 `mcs` + `mono`（实测加载 `net_4_x-win32/mscorlib.dll`）与 `net10.0` 跑同一份源码，6 颗种子 × 4 种取数方式**逐字符一致**；IL2CPP 用的 `il2cpp/build/deploy/System.Private.CoreLib.dll`（FileVersion 8.0.424，即 .NET 8）里搜到了 `CompatPrng`/`xoshiro`，与 net10 同源。所以这条**不是问题**，已降级为 🟢 并只建议加一条 5 行的廉价断言。留下这个更正，是因为"先实测再定罪"本身就是本次评估该有的工作方式。

**分层与依赖方向的实际状况**（回答"问题 5"）：

- `DataService` **确实反向依赖了 Domain** —— `DataService.cs:502-511` 调用 `建筑外形.矩形/认得出/形状清单/生成`（定义在 `Assets/Scripts/Domain/区域/建筑外形.cs`）。但这是**有意的**：`建筑外形` 是纯函数、不吃 Unity、不吃 Domain 状态，当"共享纯算法库"用是合理的。
- 更有意思的是**作者对这件事的处置不一致**：`数据模型.cs:946-947` 特意把 `世界规格` 常量**放在 Data 层而不是 Domain 的 `大世界生成器` 里**，理由原文是"这样 DataService 做数据级校验时读它，**不必反向依赖 Domain**" —— 说明作者在主动维护依赖方向；但对 `建筑外形` 却允许反向引用。**同一类问题两种处置**（#24）。
- **Domain 里的 `UnityEngine`**：全 Domain 目录用 grep 找 `using Unity*`，**只有一处命中：`Domain/品质.cs:1`**。它用的是 `UnityEngine.Color`（`品质.cs:25-37` 六个 `new Color(...)`）和 `UnityEngine.ColorUtility.ToHtmlStringRGB`（`:57`、`:65`）。**为什么验证器没发现**：因为 6 个验证器的 `<Compile Include>` 列表里**都没有 `品质.cs`** —— 它们链接的是 `数据模型.cs` + `数据解析.cs` + 具体的网格/区域/大世界文件（`Tools/大世界验证/大世界验证.csproj:14-25`）。`品质` 枚举本身在 `品质.cs:4`，而 `数据模型.cs:171` 的 `品质档 => 数据解析.枚举<品质>(品质)` 只用到**枚举名**。所以：**`品质.cs` 从未被离线编译过，那个 `using UnityEngine` 一直没被发现**。这条对游戏无害（Unity 里当然能编译），但它是"Domain 零 UnityEngine"这条纪律的**唯一破口**，而且是**靠验证器不链它才没暴露**。
- **`Domain` 里没有 `UnityEngine.Random`**（回答"问题 6"）：grep 全仓库的 `UnityEngine.Random` 只命中 3 个 **Services** 文件 —— `房间探索服务.cs:381`、`安全屋管理器.cs:148/284`、`PlayerService.cs:35/36/189/190`、`大世界探索服务.cs:134/196/204/215`。**Domain 是干净的**，所有随机都走 `确定性随机`（纯 C#）或由服务层注入。这是**做得很好的地方**。
- **哪些生成逻辑无法离线验、为什么**：
  - **`大世界探索服务.搜索()`**（`:134/196/204/215`）：扣行动点、掷 `UnityEngine.Random` 概率、挑楼型、挑房间候选、掷临时建筑种子 —— 服务层不吃 Unity 就没法跑，所以**它本身**离线不可验（**它的纯算术部分已被抽出**成 `搜索规则.cs`，`:5-12` 的文件头专门解释了为什么抽出来 —— **这是把随机缩到最小的正确做法**，属于做得好）。
  - **`房间探索服务.cs:381`** 的 `UnityEngine.Random.Range(0,100)`：同上，属于服务层，**未确认**它是不是"搜索成功率"之类的纯算术 —— 若是，也可按 `搜索规则` 的模式抽出去。
  - **`PlayerService.cs:35/36/189/190`** 的"新游戏随机世界种子"：**本来就不必离线验**（种子是入口参数，验的是"给定种子之后"的确定性）。
  - **走 `确定性随机.随机流` 的一切生成**（房间摆容器/敌人、区域摆建筑/撒敌人/撒障碍、大世界撒敌人/撒障碍、搜索落点洗牌、楼梯位）：**离线验是有效的** —— 我实测确认 Unity Mono / IL2CPP 与 net10 的 `System.Random` 序列一致（见 #14/#23 的更正）。所以本项目的离线验证在这一点上**站得住**。

### #14 🟢 **（已实测推翻，原判 🔴 有误）** `System.Random(种子)` 跨运行时**当前是一致的**

## 四、做得好的地方（含"看着怪但是刻意取舍"）

1. **`约束摆放` 是真正的通用摆放引擎**（`约束摆放.cs:1-24`）。它把"摆什么"（`Func` 回调 `建`）与"怎么摆"（区块配额 + 大件优先 + 锚点采样 + 全图补位）彻底解耦，还**明确声明了引擎只保证尝试时合法、不保证最终不变量**（`:9-11`）—— 这种"明确划出可靠性边界"的注释极少见。RNG 只走外部传入的一条流（`:8`），使确定性可证。
2. **确定性设计成体系**：`确定性随机.派生(种子, "用途字符串")` 给每类内容一条独立子流（`房间生成器.cs:74/126/284/338/527`、`区域生成器.cs:117/205/326/366`、`大世界生成器.cs:236/274/400`）。这样"加一类新内容"不会挪动已有内容的随机序列 —— 是**前瞻性的正确做法**，比"一个种子一把 Random 顺序用完"强得多。
3. **`网格数据.指纹()`**（`:359-377`）先按 (类型, 定义标识, 列, 行) 排序再拼字符串 —— **排序消除了实体表顺序的影响**，使"同种子同布局"可逐字节断言。这是可验证性的基础设施，做得对。
4. **"占格物不碰门口四邻"背后的数学论证**（`大世界生成器.cs:308-310`）：4 连通网格的割集必是 8 连通屏障，所以"占格物两两切比雪夫 ≥2"⇒ 不可能切断开阔地。**这个推理是正确的**，而且作者用它把 O(N) 次全图校验降到 1 次。看着像"偷懒/危险"，其实是**有证明支撑的性能优化**。而且作者**精确地说明了这个论证的适用边界**（`:312-313`：临时建筑是 2×2 一整块，**能**凑出屏障，所以它的落点必须逐个试放 + 校验）—— 这是**知道自己的证明在哪儿失效**，水准很高。
5. **`撒敌人` 的"占格 = true"决策 + 注释锁死**（`大世界生成器.cs:230-231`、`区域生成器.cs:317-319`）：明确写了"若做成不占格，玩家会从它身上走过去（距离 0 ≠ 1）而永远打不起来 —— 那是个隐蔽的坑，别改"。**这是把"反直觉的实现细节"升级成"带理由的设计约束"**，正是防止后来者好心办坏事的正确写法。
6. **`Domain` 层真的没有 `UnityEngine.Random`**（问题 6 的答案）。grep 全仓库 `UnityEngine.Random` 只命中 Services 层（`房间探索服务.cs:381`、`安全屋管理器.cs:148/284`、`PlayerService.cs:35/36/189/190`、`大世界探索服务.cs:134/196/204/215`）。**所有 Domain 随机都走 `确定性随机`**。这是纪律落地的正面证据。
