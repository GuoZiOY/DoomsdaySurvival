## 二、总体印象（6 句）

1. **三层的"外壳"确实抽上去了，而且抽得比移交报告的口气还干净**：点击转发、点格反馈、落点圈、闪红、
   相机夹边、迷雾三态、令牌自己走路、外观工具（摆满/摆居中/建名称/建线条/是墙/亮底）、可见性规则
   （`网格可见性`）都各只有一份；三个子类剩下的是"实体长什么样 + 右键给什么菜单"。
   新接一层（大世界）改动量实测很小：**3 个新文件 + 3 处开关覆写 + 1 个面板引用位**（`面板管理器.cs:21,141` 那一刀），
   这正是设计想要的形状。
2. **真正的重复不在三个面板里，而在"面板基类 / 探索网格面板 / 探索图层"三者的接缝上**：
   `刷新()` 与 `刷路径()` 是"每帧无条件全量重刷"，`更新池()` 会连带 `刷迷雾()` 整屏重刷，
   而"谁在这个时刻该刷"没有版本号/脏标记，只靠"调用者记得刷"（`探索图层.cs:121,536,314`）。这带来的是
   **重复计算而非错误**，量已经数出来了（见 §四）。
3. **池化的算术是可信的**（唯一抽出去、且带离线核对的区间算法 `窗口格区间`），但**池化依赖的是"相机位置"，
   `在窗口内()` 依赖的是"相机位置 + 视口尺寸"，两者在"改了窗口大小"这一维上不等价** → 存在一条真实的漏回收路径
   （`探索图层.cs:292`），以及一条"界外格在池化与非池化两条路上表现不一致"的路径（`:212-221` vs `:317-339`）。
4. **数量级是可控的**：大世界池化后地表/迷雾/交互 ≈ 3×540 = 1,620 张图（我按场景实测视口 2250×1170 重算的，
   不是文档里那句"400 槽"），物品层 ~1,100~2,600 个 GameObject 才是大头；走路时**没有每帧分配**，
   分配集中在"重建 / 换世界 / 池重排"这些离散事件上（每帧分配的项目：**未发现**）。
5. **可达性是三层最短的一块板**：探索层**没有任何键盘/手柄入口**（`玩家输入系统.cs` 只处理 F1），
   `格子探索服务.方向移动()` 这个现成的方向键入口**在 UI 层 0 引用**（全仓库只在服务里定义）；
   同时"点了没反应"的三条反馈路径（音效 / 落点圈 / 闪红 + 日志）是齐的，属于**表现层做得比操作层好**。
6. **"刻意取舍"的地方确实都写了注释**（大世界边界墙不描边、障碍不挂名称、楼/营地不吃点击、
   玩家令牌不吃点击、迷雾在物品层之上、基类 Update 不许覆写……），这些**不是问题**，我在 §六 逐条列了。

## 四、渲染 / 分配规模量化（三次进入的估算表）

### 4.1 算法（怎么数出来的）

**输入常量**：`格尺寸 = 90f`（`网格面板基类.cs:27`）；场景实测视口见 §一
（房间 2000×1200 / 区域 2250×1350 / 大世界 2250×1170）；房间网格取模板中位 **16×10**
（`房间生成器.cs:25-26`：列 8~26 / 行 6~18，文档口径写的是 16×10）；区域 **32×22**；大世界 **100×100**。

**每层每格的图数**（逐条对代码）：

| 来源 | 公式 | 代码 |

### 4.3 走路时每帧有没有分配？（逐项）

| 位置 | 结论 |
|---|---|
| `探索图层.Update()` 全部 8 个子步骤（`:118-124`） | **无分配**：`Mathf`/`Vector2` 都是值类型；`UI工具.设锚` 只写属性 |
| `跟随相机()`（:511-526） | 无分配。`new Vector2(...)` 是结构体，无 GC |
| `跟随玩家()`（:671-687） | 无分配；`实体框矩形()`（探索网格面板.cs:51-58）是遍历 `网格物品` + `字符串 ==`，只在**玩家框为 null 时**调 |

| `更新池()`（:287-315） | 无分配（池数组在 `建格子()` 一次性 `new int[池容量]`，:182-183）；字符串拼接只在溢出警告里（:310，正常不可达） |
| `刷迷雾()` / `画一格雾()`（:573-609） | 无分配（`Color` 是结构体，且值没变就不写，:608） |
| `刷路径()`（:612-651） | 无分配；`路.Count` 变化时只开关 `enabled` |
| `刷新物品()`（`网格面板基类.渲染.cs:78-114`） | **有分配**：`List<物品堆叠> 待删 = null` 惰性建（:107，只有真的删框时才建），正常走路不删框 → 不分配 |
| 基类 `Update`（网格面板基类.cs:200-244） | 走路时 `待刷新网格` 为 true → 进 `刷新网格()` 后直接 return（:206-207，`拖拽中堆叠 == null`）→ 不分配 |
| 日志面板 `追加()`（日志面板.cs:75-109） | 每条日志：`new GameObject` + `Regex.Split` + `StringBuilder` + `Regex.Replace`（:180-192）+ `Canvas.ForceUpdateCanvases()`（:141）+ 协程；**只在有消息时**（走路不产生消息，所以不进这条） |
| 房间网格面板 `更新实体框`（:186-191） | 每帧可能 `$"{实体.名称} ✓"` 拼字符串（:189）→ **只在文本变了才写**（:190），但表达式本身在每次刷新时都会构造一个新 string。60 个实体 × 3.3 次/秒 ≈ 200 个小字符串/秒（**发现 P-04**） |

**结论**：**没有"每帧分配"，也没有 LINQ**。分配集中在离散事件上：
`换世界/首次进图`（全量重建：上千个 GameObject）、`相机跨格`（池重排，无分配）、`踩到格心`（1 个 HashSet）、
`每步的实体框刷新`（每个实体的名称字符串）。
