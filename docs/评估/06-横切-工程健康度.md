## 二、总体印象

**一句话**：这是一份**文档纪律与离线验证工具链远超同规模个人项目**的工程 —— 有 20+ 篇设计/交接文档、**6 个离线验证器 + 4 个核对脚本**、约 40 条生成层不变量断言，而且**经我脚本化核对，文档里 `文件.cs:行号` 的全部引用 0 处失效、文档声称的数据条目数与 JSON 实际条目数分毫不差（269 件物品/27 文件等 12 项全对）**。

**但它的风险不在"代码烂"，而在"改坏了没人知道"**：

1. **架构约束 100% 靠自觉**。游戏四层**一个 asmdef 都没有**（`Assets` 下仅 3 个 asmdef，全在 `Plugins/MCPForUnity` 与 `Tests`）。后果已经实打实出现两处：`Domain/品质.cs:1` 破了"Domain 纯 C# 零 UnityEngine"铁律（而 4 个验证器的 csproj 恰好都没链接这个文件，所以**工具链也照不出来**）；`Data/DataService.cs:502-507` 调 Domain 的 `建筑外形`，与 `UI` 直调 `Domain` 生成器（`区域网格面板.cs:97,234,276` 等）一起，让文档画的那条 `UI ← 事件 ← Services ← Domain ← Data` 双向失效。
2. **验证覆盖严重偏科**。5 个验证器**全部指向 `Domain` 的生成算法**（网格/房间/建筑/区域/大世界），而 **`Services`（21 文件 6,171 行）、`UI`（79 文件 13,564 行）、战斗系统、存档读档 —— 这四条链路离线覆盖为零**（命令证据：扫 `Tools/**/*.csproj` 搜 `Services|UI\|Events\|Core\` → **0 命中**）。也就是**项目约 70% 的代码量在自动化验证之外**。更刺眼的是 `格子池区间核对.ps1` 用 PowerShell **重新实现**了 `探索图层.在窗口内()`（注释自称 "Mirrors … literally"）—— **验的是副本，不是代码**。
3. **静默失败模式成体系**。枚举值/字段先落地、实现后补、**校验层不拦**：`开锁方式.砸锁`（`房间探索服务.cs:337` 播报"砸锁还没做"）、技能 `出手时机="引导"`（`数据模型.cs:336`，JSON 可写但无实现）、`攻速倍率/移速倍率`（`战斗单位.cs:60-61`，永远 1f）。数据里写了这些值**不会报任何错，只是静默无效**。
4. **有一条确证的死代码**：`物品.类型 == "技能书"`（`物品网格面板.交互.cs:114`、`物品工具.cs:19`）—— 我核对了全部 JSON 的 `类型` 取值分布（12 种，**不含"技能书"**），而"技能书"在设计上是 `书籍种类`。这两处永远不可达，且 `DataService` 的 `物品.类型` 校验只覆盖"武器/防具"（`:220`），**照不出这种笔误**。
5. **没有一条标准 TODO**。`TODO`/`FIXME`/`XXX` 在 140 个文件里命中数都是 **0**；101 处"占位类"命中里绝大多数是 `占位物`（领域类型名）、`预留底行`（行列常量）、`顶部预留`（像素常量）等**被关键词误伤的正式代码**。未完成事项全部写在中文散文注释里 —— **只能靠人读，无法机器检索**。

### 3.3 耦合热点（本报告最有操作价值的一节）

**事件总线侧的不对称更值得注意**：`发布` 232 处 vs `订阅<` 45 处。发布远多于订阅本身合理（一个事件多方发），但订阅**高度集中在两个文件** —— `UI/框架/面板管理器.cs`（13 次）、`UI/HUD/HUD面板.cs`（8 次），两者合计 21/45 = **47% 的订阅**。这两个文件因而成了"全游戏状态刷新的单点"，也是任何事件的**事实测试点**。
