## 二、总体印象

1. **分层守得比预期好**：伤害公式、命中/暴击/减伤、行动条推进、意图选定、AI 抽招、目标合法性、冷却计时**全部在 `BattleService` / `战斗单位`**，UI 侧一份都没重写；`战斗单位视图` 只是把 `单位` 的字段往 Slider/Text 上搬（`战斗单位视图.cs:72~83`）。这是最难做到的一条，做对了。
2. **但"事件驱动"这句话在战斗面板里只兑现了一半**：`战斗开始/伤害/治疗/战斗结束` 走事件（`战斗沙盒面板.cs:36~39`），而**单位卡、行动条、血条、意图色、冷却遮罩、模式按钮文本这六样全部是 `Update` 轮询**（`战斗沙盒面板.cs:264~301`、`战斗轨道.cs:75~116`）。移交报告 §三 说的"事件驱动 + 轮询兜底"，在战斗里准确说是"**只轮询**"。
3. **轮询的代价不是"每帧一次"，而是"每帧 × 单位数 × 无脑重建字符串"**：`战斗单位视图.状态内容()` 每帧 `new List<string>` ×2 + 插值 + `string.Join`（`战斗单位视图.cs:144~156`），而 TMP 文本只在值真的变时才该写——这里**先造字符串再比较**（`战斗单位视图.cs:111~113`），去重去在了最贵的那一步之后。
4. **配色脱离主题**：战斗 UI 目录下 **25 处 `new Color(...)`，零处引用 `游戏主题` / `网格面板配色`**（grep 全目录）。部分值恰好等于主题值（近战飘字 = 羊皮纸白、治疗飘字 = 苔绿、技能槽·攻击 = 血烬红），是复制的巧合；意图色（金/血红/紫/灰蓝）在主题里**没有对应语义**，且与技能槽类别色互相打脸（见发现 #8）。
5. **反馈"数值变了但看不出来"的地方集中在三处**：伤害吸取（空枪/无弹药）、技能点下去失败（精力不足/武器不匹配）、防御姿态生效中——这三件事**界面上完全无痕**，只有左下日志里一闪而过。
6. **可达性（手柄）为零**：全战斗输入只有 `Keyboard.current` 硬编码（`战斗沙盒面板.cs:282~300`）与 uGUI 鼠标点击，没有 InputAction/EventSystem 导航链路，`技能槽` 连 `Selectable` 导航显式配置都没有。
7. **最反直觉的一条**：战斗中最该防的"两个层面板打架"**没有发生**（侧边栏战斗中主动藏掉角色/任务按钮，`侧边栏面板.cs:96~97`），但**F1 是漏的**——`玩家输入系统.cs:26` 无条件打开持有面板，而持有面板与战斗面板同属"可切换面板"互斥集合（`面板管理器.cs:181~186`）→ 战斗被打断（见发现 #4）。

**每帧 `GetComponentInParent<T>()` 调用数（全部未缓存）**：
- `战斗单位视图.轨道 => GetComponentInParent<战斗轨道>()`（`:44`）——**只在 `点卡()` 里用**，不是每帧。
- `技能槽.外壳 => GetComponentInParent<战斗沙盒面板>()`（`技能槽.cs:17`）——**只在按钮回调里用**，不是每帧。
- `战斗道具网格.外壳 => GetComponentInParent<战斗沙盒面板>()`（`:9`）——回调里用。
- `战斗轨道.外壳 => GetComponentInParent<战斗沙盒面板>()`（`:32`）——**每帧 ×1**（`:112` 的 `是可选目标` 处，`外壳 != null && 外壳.是可选目标(单位)`；C# 的 `&&` 短路使右侧属性只求值一次，但左侧 `外壳` 每单位求值一次 → **每帧 × 单位数**）。
- `战斗沙盒面板.刷新模式按钮` 的 `GetComponentInChildren<TMP_Text>()` ——**每帧 ×2**（`:307`、`:312`）。

> 即：**每帧 ≈ 单位数 + 2 次 `GetComponent*`**（6 单位时 ≈ 8 次/帧 = 480 次/秒）。Unity 的 `GetComponentInParent` 是沿父链 + 组件列表线性查找，单次开销虽小，但这个量级纯属白给。

### 4.2 每帧托管分配估算（算法写在括号里）

| 来源 | 每帧分配数 | 算法 |
| --- | --- | --- |
| `BattleService.推进战斗` 的 `全部单位()` | **3 次 List** | 每帧固定 3 次（`:166`/`:182`，`:231` 的 while 内每次迭代再 1 次；轮次结算那 60 秒一帧再多 3 次）+ 每次 `AddRange×2` |
| `战斗轨道.同步单位` 的 `我方组`+`敌方组`+`new[]{}` | **3 次 List/数组** | 每帧固定；数组元素为 2 个 List |
| `战斗轨道.同步单位` → `全部单位()`（面板传入） | **1 次 List** | `战斗沙盒面板.cs:268` 每帧新建 |
| `战斗单位视图.状态内容()` | **每单位 2 个 List + 1 个 Join 结果 + N 个插值串** | `片段` + `括号` 两个 List；`$"[{s}]"` 每片段 1 串；`string.Join(" ", 括号)` 1 串。6 单位（无状态时列表为空、无串）→ 有 buff 时约 3 串/单位 |
| `技能槽.刷新冷却` 文本 | **每槽 1 串**（`$"{Ceil}秒"`）+ 空串常量 | ≤6 槽 → ≤6 串/帧（冷却结束时写 `""`，字面量不分配） |

| `Keyboard` 两数组 | **2 个数组（48 B 各）** | `new[] { 6 个 KeyControl }` ×2 |

### 4.4 日志面板的额外开销（战斗特有的放大）

`日志面板.高亮数值`（`日志面板.cs:180~192`）对**每一条**日志做 `Regex.Split` + `Regex.Replace`（`(\d+)` 替换为富文本）。战斗是日志最密的场景（`发消息` 每条伤害 + 每次击败 + 每次模式切换），一条日志 = 1 次 Split + 1 次 Replace + 若干串拼接。**算法**：一场 ≈ 450~600 条 → **≈ 1000 次正则调用/场**，全部在主线程、且发生在 `发消息` 的发布回调里（同步）。

### 4.5 量化结论

- **每帧**：≈ 9 个容器对象 + ≈ 20 个 string（1.2~2.0 KB）+ ≈ 8 次 `GetComponent*` + 6 次 TMP `text` 写入 + 12 次 Slider/Interactable 写入。**没有 LINQ、没有 `Find`、没有类名 `new` 的 GameObject**（这三点做得干净——见 §六）。
- **一场**：≈ 13 个轨道对象 + 400+ 飘字 TMP + 400~600 日志条目 + ≈ 1000 次正则。**UI 层没有 `new` 战斗单位/技能数据**。
- **最值得先删的三笔**：① 每帧 3~4 次 `全部单位()` 列表（服务侧给 `IReadOnlyList`/复用缓冲即可，改 `BattleService`）；② `状态内容()` 每帧两个 List + 字符串（改成"只在 `Buffs` 版本号变化时重建"，只改 `战斗单位视图`）；③ 模式按钮每帧 `GetComponentInChildren` + 插值（改 `Awake` 缓存 + 值比较，只改 `战斗沙盒面板`）。
- **最值得先删的一笔非每帧**：飘字 TMP 的"一条一个 GameObject"（改对象池，只改 `战斗轨道`，收益 ≈ 400 次 Instantiate/Destroy → 池容量 16~24）。

### 5.2 键鼠之外（手柄）

- **全部战斗输入都是 `Keyboard.current`**（`战斗沙盒面板.cs:282~300`：escape / digit1~6 / numpad1~6 / tab / enter / space），鼠标走 uGUI 原生点击。
- **没有** `InputAction` / `InputActionAsset` / `PlayerInput` / `InputSystemUIInputModule` 的使用痕迹（grep 战斗目录无 `InputAction`）。
- uGUI 的 `Selectable` 导航（`技能槽.prefab:459` 有 `Button`）**没有显式 `Navigation` 配置**（`技能槽.prefab` 的 Button 块未读到 `m_Navigation` 的显式设置 → **未确认**是否默认 Automatic；即便是默认，也没有"手柄确认键"→ 战斗的"点卡选目标"没有任何按键等价物）。
- 结论：**当前手柄不可玩**。若要做，最小路径是 `战斗轨道` 里给"候选目标"排序后接 D-pad 左右 + 确认键（可以直接复用现成的 `循环焦点`/`释放焦点` 两个方法，把 Tab/Enter 换成 InputAction 即可）——**这两个方法已经是按键无关的**，改造成本比看上去低。

### 5.3 战斗中能不能开背包 / 角色面板

- **角色面板**：侧边栏按钮在战斗中被隐藏（`侧边栏面板.cs:96`）✅；但订阅的是 `战斗开始事件`/`战斗结束事件`（`:32~33`）→ 若战斗以"面板被顶掉"等异常方式结束（#4/#16），显隐可能不同步。
- **背包（持有面板）**：**F1 无拦截 → 会打架**（#4）。
- **浮动面板**（容器/制作/净水器/书籍）：战斗面板是 `可切换面板` 之一，浮动面板挂在 Canvas 顶层且独立（`浮动面板基类`），**未确认**战斗中是否有入口（搜索面板由 `显示结算` 在非格子层战斗时打开 `:258` → 这是**主动弹**，属设计）。这条建议单独跑一次实机核对。

### 5.4 结算表现与"回哪一层"的硬编码

- **`BattleService.返回()`（`:1290~1304`）里有一串 `if (节点 == "__房间胜利") …` 的节点名 → 服务方法 的分派**。这是**服务层**的硬编码，不是 UI 层。**UI 层没有按节点名切面板**（`面板管理器` 只订阅 `回到房间事件`/`回到区域事件`/`回到大世界事件`，`:133~142`）→ 符合报告 §六 第 37 条"服务只发意图、UI 负责切面板"的既有分工。✅ **这一点做得对**，值得记在 §六。
- **但"回哪一层"的信息链有三段硬编码**：① `格子探索服务` 的 `遭遇胜利节点 => "__房间胜利"`（`:436~437`，三层各自覆写）；② `BattleService.返回()` 的 6 个字符串比较（`:1297~1302`）；③ `战斗沙盒面板.显示结算` 里反过来查三个服务（`:252~254`）。**同一件事（这场战斗属于哪一层）在三个地方各写一遍**，正是报告 §六 第 38 条警告过的模式。当前三层都在，所以能跑；**加第 4 层（比如"楼里遭遇"单独一层）会漏改**。
