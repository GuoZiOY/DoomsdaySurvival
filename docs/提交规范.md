# 提交规范

> 只为**看得懂**服务：让 GitHub 上的读者（含招聘方）扫一眼就知道每次改了什么、属于哪类。
> 历史那 126 条 `刀NN` 提交**不改**（文档里到处是它们的短 SHA），从本规范落地之后的新提交开始执行。

## 格式

```
<type>(<scope>): <中文摘要>

<正文：为什么这么改 / 关键数字 / 验证结果>
刀次：<N>（可选，见 docs/优化实施进度.md）
```

- **type**（英文关键字，固定这 9 个）：
  | type | 用于 |
  |---|---|
  | `feat` | 新功能、新数据、新内容 |
  | `fix` | 修 bug（含"静默失效"类） |
  | `refactor` | 不改行为的结构调整 |
  | `perf` | 性能 / 包体 / 内存 |
  | `docs` | 只动文档 |
  | `test` | 验证器、门禁脚本 |
  | `chore` | 资源增删、目录、工程设置 |
  | `build` | 打包 / 依赖 / 平台设置 |
  | `style` | 纯格式（本作很少用） |
- **scope**：模块名，用中文（`战斗` / `存档` / `寻路` / `角色面板` / `资源` / `设置` …）。
- **摘要**：动词开头、一句话；**说"改了什么 + 效果"**，不要只写文件名。

## 不写什么

| 不写 | 为什么 |
|---|---|
| `20260913` 日期前缀 | git 自己存 author date，GitHub 也显示；同一天多条还会长得一模一样 |
| `v51` 版本号 | 版本用 **tag**（`git tag v0.5.0`）；写在 message 里搜不到也管不了 |
| `刀52`（主题行） | 内部批次号，外部读者看不懂 → 降到**正文/footer**，追溯能力一点不丢 |

## 一条提交 = 一个主题

- 提交前先 `git status` 看清单，**按主题分组**，别一次全提。
- **只 add 明确路径**（`git add -- <路径>`），不要 `git add -A`：仓库里长期有本地杂物（`.workbuddy/`、`评审/`）不该进库。
- 场景/预制体改动**单独一条**（里面的改动常常是手动接的线，混进功能提交里以后不好回退）。

## 提交前必须做的两件事

1. **门禁全绿**：`& ".\Tools\编译校验.ps1" -含Editor` + `目录核对` / `分层核对` / `数据引用核对` / `文档核对` / 三条`接线核对`。
2. **改完 JSON/C# 先 `git diff --numstat`**：删字段的期望值是"N 删 0 增"，对不上就是改坏了。

## 里程碑用 tag，不用 message

```powershell
git tag -a v0.1.0 -m "首个可玩版本"      # 例：能出门、能打、能存档
git push origin --tags
```
