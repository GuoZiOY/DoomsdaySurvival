# 积木化 · 组件化 · 工厂化 游戏框架设计规格

> 项目：文字奇幻rpg（灰烬镇·余烬传说） ｜ 日期：2026-08-15 ｜ 状态：已确认
> Unity 6000.4.8f1 · URP 2D · StandaloneWindows64

---

## 1. 背景与目标

现状问题：

- 现有 13 个脚本为单体脚本，系统间直接互相调用（剧情引擎直接调 UI、战斗直接调界面），耦合严重。
- **交互模型缺陷**：几乎所有交互都被压进底部「按钮区」，商店 20 件商品 = 20 个按钮，内容密度被交互形态锁死。
- **代码生成 UI**：界面结构/样式大量在代码里 `new GameObject / SetText` 构建，无法在编辑器可视化搭建。
- 加新系统（仓库/种植/锻造/公会…）需要改核心代码，扩展困难。

目标：搭建一个**积木化、组件化、工厂化**的插件式框架，为后续任意系统的添加与扩展奠定基础。用户明确列举的远期设施：商店、公会、任务、仓库、酒店、伙伴、锻造、基地、种植。

成功标准：

1. **加一个新设施 = 三块积木**（定义 + 逻辑类 + UXML 视图），核心代码零改动。
2. **杜绝代码生成 UI**：界面结构/样式 100% 在编辑器（UXML/USS）搭建；代码只做「克隆模板 + 赋数据 + 订阅事件」。
3. **交互面板化**：按钮区只负责剧情分支选项；其余游戏流程全部在「主视窗面板」内完成，面板内容可密集（网格/列表/槽位/卡片）。
4. 领域逻辑纯 C#、零 UnityEngine 依赖，EditMode 单元测试秒跑。
5. 逻辑与 UI 完全解耦，通信仅走事件总线与服务 API。

已确认的技术决策：UI 采用 **UI Toolkit (UXML/USS)**；数据表示**保留 JSON**（Resources/Data）；范围 = **框架重建 + 迁移现有内容**。

## 2. 设计原则

| 原则 | 含义 |
|---|---|
| **单向依赖** | 表现层→应用层→领域层→数据层，禁止向上调用 |
| **逻辑永不调 UI** | 逻辑只发事件；UI 订阅事件刷新自己 |
| **交互发生在面板内容上** | 不在全局按钮区；按钮区专属剧情选项 |
| **数据即积木** | 新内容 = 新 JSON 定义，不写代码 |
| **设施可插拔** | 新设施走工厂装配，零改核心 |
| **领域层纯 C#** | 可测逻辑不带 UnityEngine，测试不依赖 Play 模式 |
| **显式依赖** | 全部依赖经 ServiceRegistry 注入，测试可换假实现 |

## 3. 总体架构与分层

```
表现层  Presentation  奇幻文字RPG.UI
    │  ↓ 只订阅事件 + 调服务 API
应用层  Application   奇幻文字RPG.Services / .Facilities
    │  ↓ 只调领域 API
领域层  Domain        奇幻文字RPG.Domain    （纯 C#，零 UnityEngine 依赖）
    │  ↓ 只读数据
数据层  Data          奇幻文字RPG.Data      （JSON 加载/校验/缓存）
```

- **领域层**：玩家档案、物品堆叠、战斗规则、效果结算、任务追踪、升级曲线——全部纯 C#，可单测。
- **应用层**：服务（存档/背包/战斗/任务…）+ 设施（商店/种植…）。编排领域逻辑、发事件、暴露 API。
- **表现层**：仅 UXML 视图 + 控制器，订阅事件刷新。
- **数据层**：JSON → 模型 → 缓存 + 启动全量校验。

**命名空间为临时隔离**：旧代码占着 `奇幻文字RPG` 根命名空间（含 `剧情效果/物品数据/日志类型` 等约 20 个与新模式同名的类），新框架暂用独立根 `文字RPG.*` 避免类型遮蔽冲突。**M6 删除旧代码后，新框架转成「无 namespace」**（全局命名空间 + 文件夹分层，参照用户另一个项目「类银河恶魔城」的风格），一次性移除全部 `namespace` 声明。

## 5. 核心机制

### 5.1 服务注册表（ServiceRegistry）

`GameBootstrap`（场景中唯一组合根）在 Awake 时按声明顺序装配全部服务：

```csharp
var 事件 = new EventBus();
ServiceRegistry.Register(事件);
ServiceRegistry.Register(new DataService(...));
ServiceRegistry.Register(new SaveService(事件, ...));
ServiceRegistry.Register(new BattleService(事件, ...));
ServiceRegistry.Register(new FacilityRegistry(事件, ...));
```

任何系统 `ServiceRegistry.Get<T>()` 取依赖；依赖显式注入；测试可注册假实现。

### 5.2 事件总线（EventBus）

- 类型化事件：`金币变化` / `背包变化` / `生命变化` / `任务进度` / `战斗结束` / `剧情推进` / `日志` 等。
- **日志也是事件**：任何系统 `事件.发布(new 日志事件(类型, 文本))`，日志视图订阅渲染——消灭全代码的 `界面.记录日志(...)`。
- **异常隔离**：发布时逐个 handler try/catch，单个订阅者崩溃不影响其他订阅者、不中断发布。

```csharp
事件.订阅<金币变化事件>(e => 金币文本.text = $"{e.数量} 金");   // UI 只订阅
事件.发布(new 金币变化事件(玩家.金币));                          // 逻辑只发事件
```

### 5.3 存档服务（SaveService）

- 玩家档案 + 当前节点 + 游戏时间整体 JSON 快照（沿用 PlayerPrefs 思路，可换文件存储）。
- 每个设施可声明 `IFacilityState`（可序列化），存档时统一收集、读档时回填。**新增设施无需改存档代码**。

### 5.4 数据服务（DataService）

- 从 Resources/Data 加载全部 JSON，缓存为模型字典。
- **启动全量校验**：所有跨引用（剧情→节点/敌人/物品/设施、区域→敌人、地点→设施）缺失即输出错误清单并阻止进入游戏，不静默。

## 6. 服务 vs 设施（核心区分）

| | 服务（Services） | 设施（Facilities） |
|---|---|---|
| 本质 | **无 UI 的能力** | **有 UI 的交互壳** |
| 例子 | BattleService / InventoryService / QuestService / EconomyService | 商店设施 / 种植设施 / 锻造设施 |
| 调用关系 | 设施调用服务 | 设施调服务 → 服务发事件 → 设施 UI 刷新 |
| 可插拔 | 加一个服务 = 一个积木 | 加一个设施 = 三块积木 |

战斗/背包/任务是**服务**（各处共享的逻辑）；商店/种植/锻造是**设施**（玩家的交互界面）。设施代码几乎只有「调用服务 + 渲染视图」。

## 7. 设施框架

### 7.1 设施定义（Data/facilities.json）

```json
{
  "设施": [
    {
      "标识": "商店",
      "名称": "商店",
      "描述": "购买补给与装备",
      "逻辑类型": "商店设施",
      "视图": "UI/Facilities/商店.uxml",
      "数据": "Data/facility_shop.json",
      "地点": ["灰烬镇"]
    }
  ]
}
```

### 7.2 设施工厂与注册表

```csharp
foreach (var d in 数据服务.加载设施定义())
{
    IFacility 实例 = 设施工厂.创建(d);      // 按 逻辑类型 反射实例化 + 挂视图
    设施注册表.注册(d.标识, 实例);
    d.地点列表.ForEach(地点 => 设施注册表.挂接到地点(地点, 实例));
}
```

- **地点挂接**：`设施注册表` 维护「地点 → 设施列表」索引（由定义中的 `地点` 字段驱动）。地点面板/地图按此索引生成设施入口，无需硬编码。新增设施只需在定义里写 `地点` 字段即自动出现在对应地点。
- 新增设施不改工厂代码。

### 7.3 设施生命周期（IFacility）

```csharp
public interface IFacility
{
    string 标识 { get; }
    void 进入(FacilityContext 上下文);        // 订阅事件、恢复状态、显示视图
    void 退出();                              // 取消订阅、导出状态
    void 刷新();                              // 数据变化时刷新视图
    IFacilityState? 导出状态();
    void 恢复状态(IFacilityState 状态);
}
```

### 7.4 剧情与设施的关系

- 剧情节点回归纯粹：只做文本、分支、效果、跳转。
- 现有 `购买:xxx` / `学习:xxx` / `__出售` / `任务:xxx` 等特殊目标**全部替换为 `设施:商店` 等**。
- 设施退出时经上下文返回剧情节点。剧情是主线骨架，设施是可复用空间。

### 7.5 设施状态存档

各设施经 `导出状态()` 上报自己的存档片段（种植存地块进度、仓库存库存、伙伴存好感度），SaveService 统一收集。

## 8. UI Toolkit 框架

### 8.1 铁律（杜绝代码生成 UI）

> 禁止在代码里 `new VisualElement / new GameObject / new RectTransform / SetText` 搭建界面结构或样式。
> 界面结构一律在 UXML，样式一律在 USS。代码只允许：**① 克隆编辑器做好的 UXML 模板 ② 给元素赋数据 ③ 订阅事件**。
> 动态列表的「一行」也是 UXML 模板：ListView 的 item 模板来自独立 UXML，代码只克隆 + 填数据。

### 8.2 交互模型（面板化）

- **按钮区只负责剧情分支选项**（叙事分支天然少而有限）。
- **其余游戏流程全部在主视窗面板内完成**：面板承载密集内容（商品网格、背包格子、地块槽位、配方列表、入口卡片墙），交互发生在面板内容上。
- 主视窗 = 面板宿主；面板可嵌套、可带返回、可滚动。

```
┌──────────────────────────────────────────────┐
│  HUD（常驻：生命/金币/时间/地点）              │
├──────────────────────────────────────────────┤
│   主视窗（面板宿主）——按上下文切换面板          │
│   · 剧情模式 → 叙事文本面板（底部少量选项）    │
│   · 设施模式 → 内容密集面板（网格/列表/槽位）  │
│   · 地点模式 → 设施入口卡片墙                 │
├──────────────────────────────────────────────┤
│  日志栏（可折叠侧栏）                         │
└──────────────────────────────────────────────┘
```

### 8.3 视图管理器（ViewManager：面板宿主 + 导航栈）

- 持久 UIDocument（根容器）+ 当前视图栈。
- `视图管理器.打开(视图标识, 上下文)`：查视图表 → 克隆 UXML → 实例化控制器 → 进栈；`返回()` 出栈。
- 视图标识 → UXML 路径 + 控制器类型 的注册表映射。
- 动画双轨：**USS transition** 用于结构性转场（面板进出/布局变化）；**DOTween** 用于交互反馈（按钮点击弹性、面板显隐缩放）——DOTween 可直接用于 UI Toolkit（项目已含 `DOTweenModuleUIToolkit`，补间 VisualElement），新旧代码同在 Assembly-CSharp、可直接 `using DG.Tweening;`。

### 8.4 控制器（ViewController）

```csharp
public abstract class ViewController : IDisposable
{
    protected VisualElement 根;
    protected EventBus 事件;
    protected abstract void 绑定视图();   // uxmlQuery 拿引用 + 订阅事件
    protected abstract void 解绑();       // 取消订阅（防泄漏）
}
```

### 8.5 数据刷新双通道

- **通道 A（事件驱动，主力）**：控制器订阅事件总线 → 更新元素。
- **通道 B（列表数据源）**：`ListView` + 可观察集合；item 结构来自 UXML 模板，代码只克隆 + 绑数据。

### 8.6 控件库（UI/Controls/）

- `属性行.uxml`（标签+数值+变色）、`物品条目.uxml`（图标+名称+数量）、`日志条目.uxml`（时间戳+类型化着色）、`按钮.uxml`（主/次/危险变体）、`商品卡片.uxml`、`背包格.uxml`、`地块槽.uxml`、`配方行.uxml`、`设施入口卡片.uxml`。
- 全部 UXML 模板，任何界面直接引用。

### 8.7 主题（USS 变量）

沿用现有暖暗色主题，统一 USS 变量（`--金:#d9a441`、`--危险:#c7473d`、`--成功:#7fae6a` 等），一套变量全游戏通用。字体沿用 `游戏主题` 的加载链方案。

## 9. v1 范围与构建顺序

```

```

**v1 设施范围：迁移 4 个（商店/训练场/任务板/酒店）+ 新增 2 个（仓库/种植）。**
公会、伙伴、锻造、基地为远期设施（框架已留槽位，届时各加三块积木）。

## 10. 现有内容迁移

- **剧情 story.json**：节点/选项/效果/战斗原样保留；`购买:`/`学习:`/`__出售`/`任务:` 等特殊目标替换为 `设施:xxx`。
- **地图 map.json**：地点新增 `设施` 数组，地点视图数据驱动生成设施入口。
- **其余 JSON**（物品/敌人/技能/任务/区域）：结构基本保留，字段仍中文。
- **迁移检查器**（Editor 脚本）：迁移后全量校验引用一致性，一次跑通。

---

## 11. 错误处理

- 启动全量校验，缺失引用输出错误清单并阻止进入游戏。
- EventBus 异常隔离：单订阅者崩溃不影响其他订阅者。
- 日志即事件：错误/警告/系统消息统一走 `日志事件`。

## 14. 明确不做（YAGNI）

- 不做网络/多人。
- 不做 Addressables（v1 内容量小，Resources 足够；迁移方便再换）。
- 不做 ECS/DOTS。
- 不做程序化 UI 生成（正是要杜绝的）。

## 15. 风险与开放问题

1. **UI Toolkit 运行时数据绑定**：优先采用「事件驱动刷新」主力通道，`dataSource` 原生绑定仅在有把握处使用，避免绑定引擎边界问题。
2. **字体中文覆盖**：沿用 `游戏主题` 的字体加载链（Silver SDF → 系统字体兜底），迁移到 UI Toolkit 时需验证 TextElement/Text 字体设置。
3. **迁移后回归**：M4 迁移完成后需全流程手测（序章→灰烬镇→商店/训练场/任务→战斗→结局）。
4. **面板嵌套深度**：v1 限制导航栈 ≤ 3 层，防嵌套失控。
