## 一、目标结构

```
【现在】大世界（节点网图，map.json 不存在 → 空字典，纯占位）
           ↓ 打开野外面板事件（快速测试面板 直接调 进入区域(标识, 随机种子)，绕过 地图服务）
        区域网格 32×22 ──→ 建筑（楼层 + 楼梯间）──→ 房间
        （区域 = 一屏网格，每次进去随机种子）

【目标】
        大世界 · 100×100 格子网格（令牌 / A* / 逐格推进 / 三态迷雾 / 相机跟随 —— 全部继承 格子探索服务）
          ├─ 区域副本（多格形状掩码占地，如 6×5）
          │     · 布局种子固定：派生(世界种子, 区域标识) → 同一存档永远同一套楼
          │     · 解锁条件（未解锁 → 地图上可不见 / 或可见但进不去 + 提示）
          │     · 独立重置计时：布局不变，内容（容器/敌人/尸体/门锁）按计时刷新
          │     ↓ 走到占地任意一格
          │   区域网格 32×22（原样复用）──→ 建筑（楼层）──→ 房间（原样复用）
          ├─ 临时建筑（大世界「搜索」在半径内生成，一次性，不刷新）
          │     ↓ 走上去
          │   建筑 / 房间（复用同一套）
          └─ 营地 = 安全屋面板（进屋 = 现有 返回营地 那条路）
```

**结构层级从「四层」变成「五层」**，但**只有最外面一层是新的**：

```
大世界（新）→ 区域（已有）→ 建筑（已有）→ 房间（已有）
```

## 三、关键技术冲突与解法

### 3.1 ★ 区域怎么"可重复刷"（v51 期间做过一次**设计纠正**，看这节）

#### 先说结论

**「副本」只是我用的一个比喻，不是要照搬刷宝游戏那套。** 实际口径（用户 2026-09-12 明确）：

> 不需要标记区域已通关，也不需要重置计时。**每次从安全屋出发新的，回来后重置。**

而这条**正是 v48/v49 就定好的规矩**，一行新代码都不用写：

```
容器战局数据（已生成内容 / 已翻标记 / 尸体容器）
视野记忆   视野记忆[种子#模板]
门锁态     已解锁门[当前种子#门标识]
楼层缓存   Dictionary<"层#序号", 网格数据>
→ 进房间 / 出房间 / 换房 都**不清**；**回安全屋**（打开营地事件）才清
```

于是「区域可重复刷」= **固定种子（刀3 已做）+ 现有的回安全屋重置（早就有）**，两件事凑齐，机制就完整了：

| 要的效果 | 靠什么 |
|---|---|
| 同一存档里那片区域**永远同一套楼** | `区域布局种子 = 派生(世界种子, "区域:" + 区域标识)`（刀3） |
| 每次出发**资源/敌人/门锁都是新的** | `打开营地事件 → 回安全屋清战局()`（v48/v49 原有） |
| 想再刷一遍 | 走回安全屋门口 → 再走过去（**赶路本身就是要付的时间成本**：5 游戏分钟/格） |

#### 我原本设计错了什么（留档，免得下次又绕回来）

我一开始把"可重复刷"理解成刷宝游戏那套，于是造了两套东西，**都已删**：

| 我造的东西 | 为什么是错的 |
|---|---|
| **`区域模板.重置小时` + 逐帧重置计时** | "什么时候刷新"根本不需要一个计时器 —— 时机就是**回安全屋**。多一个计时器就多一套"代次/剩余分钟"的随档状态、多一条时间流，全是白造。 |
| **「两把钥匙」**（布局种子 + 战局代次进内容键） | 这套是为了调和"布局固定"与"内容能重置"而生的。可既然重置时机就是回安全屋、而回安全屋**本来就把所有内容键清干净了**，第二把钥匙（代次）完全多余。**一把钥匙（布局种子）就够了。** |
| **`前置区域` 解锁条件 + 「标记区域已通关」** | 用户明确"**不需要标记区域已通关**"。本作没有"通关"这个概念（资源是反复刷的，不是一次性的），留着它只会变成一道永远打不开的门。 |
| **`区域模板.稀有度`（资源档）** | 固定区域给好资源，靠**它自己 `建筑[]` 里列什么楼**就够了（纯数据）；不需要多一个没人读的档位字段。 |

> **教训**：用户给的词（"副本"）是**比喻**，不是要求照搬那套机制的原型。
> 遇到比喻先去问"你要的是哪个**效果**"，而不是照着比喻的原型去补全它应有的一切。
> 这一次的代价是：写了一份 130 行的"两把钥匙 + 重置计时"设计（本文档原先的 §3.1 全文），
> 幸好**还没实现**就被纠正了 —— 只在数据模型上留了三个空字段（现已删）。

#### 「回来后重置」这条链要真的清干净（这才是刀5 的实事）

清战局的**唯一**时机是 `打开营地事件`。而玩家**不一定是从楼里走出来的** ——
他可能是**从大世界直接走到安全屋门口**回去的（`大世界探索服务.抵达格` → 发 `打开营地事件`），
那条路**根本不经过 `离开世界()`**，所以 `离开前()` 不会跑。

于是"所有本趟的表都必须在 `清战局()` 里清"是一条**硬约束**。刀5 核了一遍并补上了漏的两张表：

```
房间探索服务.清战局():
    搜索?.清空战局()        // 已生成 / 已搜索 / 实例定义 / 尸体定义 / 尸体序号
    已解锁门.Clear()
    楼层缓存.Clear()
    敌人身上的钥匙.Clear()   ← 刀5 补：原先只在 离开前()
    已察觉.Clear()           ← 刀5 补：原先只在 离开前()
    本次战斗来自房间 = false  ← 刀5 补：原先只在 离开前()
```

> 这两张表原先"漏"了但**恰好没出事**：`放钥匙()`（每进一间房调）开头会先 `敌人身上的钥匙.Clear()` 重新决定，
> 而 `已察觉` 攥着的是**上一轮**的 `网格实体` 对象（每轮重新生成 → 引用不会误命中）。
> 所以不是"修 bug"，而是把「回安全屋 = 这一趟彻底结束」这条**不变量**补成真的 —— 靠巧合成立的东西不算保证。

#### 一个连带后果：钥匙位置也固定了

`放钥匙()` 的注释写着「按种子随机（同一趟同一间房固定，**重玩会变**）」。
刀3 把区域种子固定住之后，**这句注释就不再成立**：钥匙每次都在同一处（同一个种子派生同一个答案）。
这与"布局固定"是自洽的，但注释得改对，免得后人以为钥匙会变。

### 3.2 ★ 100×100 的渲染：视口虚拟化

**证据**（逐格建图，与格数成正比）：

| 层 | 建法 | 32×22 | **100×100** |
|---|---|---|---|
| 底座层 底格（`网格面板基类.渲染.cs:59-61`） | 每格 1 张 | 704 | **10,000** |
| 线层 分隔线（同文件 `:183-196`） | `(列+1)×行 + (行+1)×列` | 1,462 | **20,200** |
| 地表层（`探索图层.cs:117-129`） | 每格 1 张 | 704 | **10,000** |
| 迷雾层（同文件 `:131-137`） | 每格 1 张 | 704 | **10,000** |
| 交互层（同文件 `:139-148`） | 每格 1 张 + 1 个 `探索格点击` | 704 + 704 组件 | **10,000 + 10,000 组件** |
| **合计** | | **≈4,278 张** | **≈60,200 张 + 10,000 组件** |

#### 解法 A：大世界免建底格 / 格线（省 30,200 张）

地表层本来就**逐格盖满**，底座层那 10,000 张底格与线层那 20,200 条格线在大世界上**完全看不见**。

给 `网格面板基类`（或 `探索网格面板`）加一个开关：
```csharp
// 只**新增**字段；不动任何 [SerializeField]，派生类原字段原样留着（红线 #1）
protected virtual bool 建底格 => true;      // 大世界覆写 false
protected virtual bool 建格线 => true;      // 大世界覆写 false
```
`刷新网格()` 里那两处循环按开关跳过。**对房间层/区域层零影响**（默认 true）。

#### 解法 B：地表 / 迷雾 / 交互 三层改「格子池」（省到 ≈1,400 张）

窗口 1720×960 → 可见约 20×12 格；**只实例化窗口 + 1 屏边距**的格子（约 26×18 = 468 格）：

```
格子池[i] = { Image 图, int 格列, int 格行 }     // i = 池内下标，与"格坐标"解耦
每帧（相机移动超过 1 格 或 换了世界）：
    算出窗口覆盖的格子区间 [列0..列1] × [行0..行1]
    对区间里每个格：从池里取一张图 → 摆到该格 → 按该格状态重画；用不到的图 enabled = false
```

要点：
- `探索图层` 已经有 `视口`（RectMask2D）/ `在窗口内()` / `跟随相机()` / `相机位置` 这套骨架 → **虚拟化是顺着它加，不是推翻**
- **`在窗口内()` 的点击防线照旧保留**（RectMask2D 只裁画面不裁 raycast，见 开发注意事项 #19）
- 池容量要**动态下限**：网格比窗口小（房间层 16×10）→ 池 = 全格（退化成现在的行为，**房间层零变化**）；网格比窗口大 → 池 = 窗口 + 边距
- 令牌走路的 `视觉位置` 与格子池无关（令牌是物品层的一个实体框），不受影响
- 迷雾 / 地表 / 交互三层共用一个「盖住窗口」的格子区间 → 一次算、三层用

**收益**：大世界 ≈ 1,400 张图（比现在的区域层还轻）；**副作用是好的** —— 以后区域层想做更大的片区、房间层想做超大楼，都不用再改。

### 3.3 种子派生链（一条线管到底）

```
玩家档案.世界种子                       ← 新游戏随机（沿用 户型种子 的做法，读档恢复）
   └─ 区域布局种子 = 派生(世界种子, "区域:" + 区域标识)          ← 永远固定
        └─ 楼种子   = 派生(区域布局种子, 楼标识)                  ← 现有 区域探索服务.进楼 已在做
             └─ 层种子   = 派生(建筑种子, "F{层}")                 ← 现有 建筑生成器
                  └─ 房间种子 = 派生(建筑种子, "F{层}#{序号}")      ← 现有 建筑生成器
   └─ 临时建筑种子 = 派生(世界种子, "临时:" + 序号) 或 当场随机      ← 一次性，无需固定
```

> **没有第二条链**。v51 早期设想过 `战局代次 = 玩家档案.副本状态[区域标识].代次`（只进内容键），
> 随"重置计时 + 两把钥匙"一起作废（§3.1）：重置时机就是回安全屋，而回安全屋本来就把内容键清干净了。

**注意**：`区域探索服务.进入区域(标识, 种子)` 现在是**外面传种子**（快速测试面板 传随机、面板管理器 传 `Random.Range(1,999999)`）。
改造后**由 大世界探索服务 传 `派生(世界种子, 区域标识)`**，`面板管理器` 那条 `Random.Range` 必须删掉 —— 否则同一片区域每次进去都不一样，副本就无从谈起。

### 3.4 大世界搜索 → 临时建筑

```
玩家在 大世界 点「搜索」（HUD 按钮 / 侧边栏 / 大世界面板上的按钮）
   ↓ 前置校验：行动点 ≥ N、不超重？（口径见下）
   ↓ 扣 行动点 + 推进游戏分钟（走 世界时间管理器）
   ↓ 半径 R 内找**可放置的空格**（扫半径内的空格，排除：已有区域占地 / 已有临时建筑 / 障碍 / 界外）
   ↓ 按概率决定"这次有没有"（0~1 个）→ 有则掷一个空位落地
临时建筑实体（网格实体类型.建筑，占地 = 小掩码 1~2 格）+ 一次性种子
   ↓ 走上去 → 复用 区域探索服务.进楼 那条路（建筑模板优先，退化成一个房间模板）
   ↓ 探索完 / 离开 → 实体消失（"一次性、不刷新"）
```

**待定的调参数**（写进 `世界.json`，不写死代码）：

| 参数 | 建议初值 | 说明 |
|---|---|---|
| `搜索行动点` | 10 | 与房间「首次搜索容器」的 10 行动点对齐（v48 定的） |
| `搜索游戏分钟` | 30 | 现实里约 1 秒（30 游戏分 ÷ 30） |
| `搜索半径` | 4 格 | "角色半径内" |
| `搜索出现概率` | 60% | 失败也给反馈（"翻了一圈，什么也没有"） |
| `临时建筑保留` | 一次性 | 进去出来就消失（可在数据里改成保留 N 分钟） |

**与固定副本的定位差异**：临时建筑给**普通资源**（现有 `搜索_地图类型` 的常规容器池）；固定区域副本给**稀有资源**（靠 `区域模板` 指到更高级的 `建筑模板` / 容器池）。这条差异靠**数据**表达，不靠代码分支。

> ✅ **v51 刀13 已按这条差异补上硬约束**（设计 + 实测见 **`docs/大世界搜索约束设计.md`**）：
> 光靠"数据上定位不同"是不够的 —— 当时 `挑临时建筑定义()` 是**从 `建筑模板` 全表等概率抽**，
> 于是第 1 天就能在安全屋门口刷出 `市立医院`/`城西分局`/`纺织厂`（枪弹/血清/图纸），
> 把三个区的 `天数≥3/6/10` 解锁门整个架空。现在有三条约束：
> ① **局部枯竭**（翻出过的地方再搜 60%→12%，枯竭格不给放）② **越翻越累**（第 N 次 `10+(N-1)×4` 点，110 点只够 5 次）
> ③ **楼型白名单 + 禁区清单 + 允许地图类型**（临时建筑永不出区专属楼型，容器池也只许引用普通地图类型）。

### 9.2 ★ 两个设计决定（值得记下来的）

**① 区域 = 占格 `true` + 只有门口那一格能走**（不是"整片能踩过去"）
最初想的是"区域是一块能踩上去的街区，踩到任意一格就进副本"。否决理由：**那会让"路过"等于"进入"** ——
100×100 的城里横穿一片街区就被拖进副本，玩家没法单纯赶路。
改成与"楼门长在楼上"同一套直觉：整块挡路、**门口那一格**能站能走 → 走上去进副本。
代价是 `网格数据.占位()` 的门口格豁免要从"只认建筑"扩到"建筑 + 区域"（一行）。

**② 门口格的取法上移到 `建筑外形.底边中点`**
区域层的楼门、大世界层的区域门，用的都是"掩码最靠下那一行里最长连续段的中间那格"。
原本这段逻辑私有在 `区域生成器` 里，大世界再抄一遍就是"同一条规则写两遍"（项目已经吃过这个亏）。
抽到 `建筑外形` 后两处共用；`掩码 == null` 按纯矩形处理，与原 `覆盖()` 写法**逐字等价**。

### 9.3 ★ 验证器抓出来的真 bug：区域门口被障碍堵死

**症状**：`大世界验证 50` 报平均 **撤回 3.1 / 世界**（障碍 200 条清单只撒下 196.9 条）。

**推理**：障碍被强制"彼此切比雪夫距离 ≥ 2"，而 **4 连通网格的割集必须是一条 8 连通屏障**（对偶关系）——
障碍之间永远 8 不相邻，所以**障碍在数学上不可能切断开阔地**。那"连通被破坏"就必有别的来源。

**根因**：`可撒障碍` 漏了一条留空规则。区域门口格长在区域占地的**底边**上，左/右/上三面都是区域实体（挡路），
**唯一出路是它下面那一格**。那格一旦落一个障碍，门口格就成了"能站却走不到"的孤岛 → 连通分量 +1。
（`区域生成器.可撒障碍` 早就为"楼门四邻"写了这条；大世界这边漏了。）
而回滚循环是从**最后撒的**开始撤，所以一个堵死的门口会让它白撤好几个才找到真凶 → 平均 3.1。

**修法**：`可撒障碍` 增"不压区域门口四邻"。

**结果**：`撤回 0.0 / 障碍 200.0 / 失败 0`（50 种子）。

**顺带加固的断言**（原来抓不到这个 bug，因为它只断言了"可通行"）：
1. 区域门口格必须**从入口可达**（`可达.Contains`），不只是"可通行"；
2. **`撤掉的障碍` 必须为 0** —— 连通校验只是"万一"的保险，触发即代表真 bug，直接判失败。

> 教训写在 `可撒障碍` 的注释里了：**"可通行" ≠ "走得到"**。凡是"三面被围、只有一个出口"的格子（门口、楼梯口、门内侧），
> 留空规则必须保护它**和它的出口**，断言也必须查**可达性**而不是可通行性。

`格子池化` 还带一个额外条件：**网格装得下窗口时一律走全格**（池化只在网格比窗口大时才有意义），
所以就算覆写成 true，小网格也还是老路径。

### 11.2 ★ 池化最关键的一处：两套判据必须一致

池化把"格坐标"与"池槽下标"**解耦**（池槽只有下标，它此刻显示哪一格记在 `池格列/池格行`），
于是同一个问题出现了两份算法：

- **点击判据** `在窗口内(c, r)` —— 早就有了（RectMask2D 只裁画面不裁 raycast，所以必须自己拒绝窗外点击）
- **建池判据** `窗口格区间(外扩)` —— 新写的，把 在窗口内 的两条不等式反解成"列/行范围"

两者一旦不一致，表现是**"看得见却点不到"**或**"点了错一格"** —— 光看代码极难发现的一类 bug。
所以做了两件事：

1. `窗口格区间()` 成为**唯一**的范围算法，`更新池` 与自检共用；
2. 重建时跑一次 `自检池覆盖()`：把"在窗口内 为真的格"与"池区间"**逐格对一遍**，
   不一致就 `Debug.LogError` 报出具体是哪一格。10,000 次纯算术、只跑一次，代价可忽略。

顺带：`在窗口内()` 的取值范围被证明是 `窗口格区间(池边距=2)` 的子集（`c > (-x₀)/格 - 1` ⇒ `c ≥ floor(-x₀/格) - 1 ≥ 首列`），
`池边距 = 2` 就是给这条不等式留的余量。

### 11.3 池容量怎么定

```
池容量 = min( (ceil(窗宽/格) + 1 + 池边距*2) × (ceil(窗高/格) + 1 + 池边距*2), 列×行 )
```

1720×960 窗口 / 格 90 → `(ceil(19.1)+1+4) × (ceil(10.7)+1+4)` = **25 × 16 = 400 槽**（≈1,200 张图，比现在区域层的 4,278 张还轻）。
池不够用时**不崩溃**：先 `Debug.LogWarning` 报出"这一屏需要更多、边上会缺格"并给出该调哪个数，再少画那几格。

**这个容量是"刚好够"而不是"随便给大"** —— 实测（`Tools/格子池区间核对.ps1`）显示，
四种窗口下"最坏区间格数"都**正好等于**池容量：

| 窗口 | 池容量 | 最坏区间格数 | |
|---|---|---|---|
| **1720×960（项目默认）** | 400 | **384** | OK |
| 1280×720 | 260 | 260 | OK（贴边） |
| 2560×1440 | 714 | 714 | OK（贴边） |
| 900×600 | 180 | 180 | OK（贴边） |

因为 `floor((窗宽-x₀)/格) - floor(-x₀/格) + 1 ≤ ceil(窗宽/格) + 1`，容量公式就是这条上界的取值 ——
所以"池不够用"那条警告正常情况下**永远不该出现**；一旦出现，说明两份判据被改歪了（正是它要报的）。

### 11.3.1 这个"最大格数"我一开始算错了

我手算 1720×960 时得出"最坏 22×13 = 286 格"，写进文档后**又写了脚本去核对**，实测是 **384**。
差了近 100 格 —— 因为 `floor` 在两端各能多进一格（x₀ 为负时 `floor(-x₀/格)` 与小窗口的取整方向不同），
手算很容易漏。**结论：区间类的东西不要靠手算，写个脚本把边界位置全扫一遍。**
（这条也顺带说明：如果当时按 286 去给容量，1280×720 那档就会真的缺格。）

> 教训有两条：
> 1. **绝不用 `Get-Content` / `Set-Content` 改含中文的 UTF-8 文件** —— 一律走 `[IO.File]::ReadAllText/WriteAllText` 并**显式指定 UTF8**；
> 2. **验证式要能区分"删干净了"和"文本被我毁了"** —— 只查"目标字符串还在不在"是不够的，
>    必须同时验 **JSON 能否解析** 与 **中文是否完好**（我这次就是把这三条都验了才发现事故）。
> 另：改动含中文的文件后，**先看 `git diff` 的形态**（"9 删除 / 0 新增"这种）比看运行结果更早暴露问题。

### 16.4 大世界街道敌人（`格子探索服务` 上移之后才有意义）

- `世界模板` 增 `敌人[]`（`{ 定义标识, 数量 }`）；`世界.json` 填 感染者×6 / 流浪狗×4 / 变异鼠×3
- `大世界生成器.撒敌人()`：撒在自由格上，**占格 = true**（挡路）
  > 为什么必须占格：`检查遭遇` 判的是"**正交相邻**"（距离 1）。不占格的话玩家会**从它身上走过去**（距离 0）而不触发遭遇 —— 隐蔽的坑。
- 敌人与障碍**共用一条判据** `可撒单个占格物()`：不压区域/营地 · **不碰任何门口格及其紧邻八格** · 与其他占格物隔 ≥1 格
  （隔 ≥1 格 ⇒ 凑不出 8 连通屏障 ⇒ 数学上不可能切断地图；这条推理在刀2 已经建立，敌人直接复用）
- 连通兜底统一成 `保证连通()`：破了**先撤障碍（装饰）、还破再撤敌人（能打的）**，两个计数分开报
- 敌人显示名由**服务层**从 `enemies.json` 补（Domain 不认识数据服务，生成器先塞 `定义标识`）
- 遭遇 → 战斗 → 胜/败 → `回到大世界事件` → 面板切回大世界；打赢留在原地一具可搜尸体（与房间层同一套）

### 16.5 ★ 这一刀验证器抓出的两个错（都是"断言写错"而不是"代码写错"）

1. **`生成()` 的改动没生效**：我改 `生成()` 加"撒敌人 + 保证连通"那次编辑**失败了**（工具报"文件未读"），
   我没有重试 → 结果是**敌一只都没撒**。而**刚加的断言立刻报**「敌人 0 ≠ 期望 13」。
   > 这条正是"**先写断言**"的价值：如果只靠肉眼看代码，`撒敌人()` 函数明明写得好好的，很难发现它**根本没被调用**。
2. **敌人"可达"断言写错了**：第一版断言"敌人自己那一格在可达集里"，20 个种子报了一半失败。
   原因是敌人**占格** → 它自己那格不可通行 → 永远不在可达集里。
   要断言的是"**它旁边至少有一格走得到**"（遭遇是走到相邻格才触发的）。
   > 教训：断言的对象要选**真正有意义的那个不变量**（"能不能走到它旁边"），
   > 而不是"看起来相关"的那个（"它自己在不在可达集里"）。
