### 顺手抓到并修掉的两个**静默结算错**（都不是审计报告里已有的条目）

`结算回写` 的口径是「生命/行动点**以战斗单位为准**」→ 任何在战斗中**直接改 `档案.生命/行动点`** 的地方
都会被它反向覆盖。顺着这条不变量一查，撞到两处：

1. **失败惩罚形同虚设**（新发现）：`结算失败惩罚` 把档案设成"回营地半状态"，紧接着 `结算回写`
   就用"倒下时的 0 血"覆盖 → 玩家**顶着 0 血**回到探索层，而日志照样说"挣扎着逃回安全处"。
   已修：半状态**同时写进战斗单位**。
2. **升级恢复被抹掉**（汇总方案 D5，报告 04 #5）：升级时 `成长管理器` 把档案抬到半状态，战斗单位不变
   → 玩家看到"升级/+3 属性点"，血和行动点一动不动。已修：快照差值补到战斗单位（报告 04 的建议做法）。

两处都写进了 `结算回写` 上方的**不变量注释**：以后在战斗中改档案生命，必须同步战斗单位。

## 一之四、刀18 · 格子层 UI 的性能（用户点名 `UI/探索` 的几个网格脚本）

> 用户的问法是"这几个网格脚本能不能优化"。做法：**先量、再改、改完给判据**（不写"感觉更快了"）。

### 先证伪了一条我自己想改的

`探索图层.跟随相机()` 每帧 `Vector2.Lerp` 再无条件写 `anchoredPosition`。我原本打算改成
"贴近目标就吸附 + 值没变就不写"，理由写好了："指数插值永远差一点点 → 每帧置脏 → 整个网格每帧重建画布"。

**离线算了一遍（单精度 float 模拟 60fps）**：第 **84 帧（≈1.4 秒）** 值就**不再变化**（收敛到距目标 3e-8 px，
低于 float 分辨率 ≈2e-8）→ 静止时并不会持续置脏。**这条不成立，没有改**。
（教训：`Vector2.Lerp` 在 float 下会**收敛到定点**，不是"永远在动"。差点把假论断写进注释。）

### 真正量出来的三处开销（离线实测，不是估）

| # | 位置 | 实测/推导 | 改法 |
|---|---|---|---|
| 1 | `探索图层.刷路径` 的池槽分配 | **每走一步要重摆 16 张路径图**（点线同样 ~15 张）；因为走路时路径每步从**队首**缩短一格，而分配是"从头数"→ 几乎每张图都改画到另一格 | 改成**从终点往前分配**（终点恒在 0 号槽）：同样一条 30 格直线走完，**每步改画 16 张 → 1 张**（离线脚本对拍两种分配得出） |
| 2 | `探索图层.刷迷雾` | 任何 `刷新()` 都**无条件全网格重画**：区域层 32×22 = 704 格 × 每格 `服.档()`（encode + 两次 HashSet 查）。而"点一格格子""显示事件刷新"这些路径**根本不改视野** | 服务侧加 `视野版本`（`刷新视野()` 自增）；`刷迷雾` 只在**版本变了 / 压暗变了 / 强制**时才画。安全性已核：改了 `当前可见/已探索/当前时段` 的入口**全部**紧跟 `刷新视野()`（三个进入流程逐条看过），`重建()` 里把去重键作废，池重排用 `刷迷雾(true)` |
| 3 | 三个探索面板的 `更新实体框` | 每次刷新对**每个实体**做一次 `框.根.GetComponent<CanvasGroup>()`（区域层一次全实体遍历 = 700+ 次组件表查找） | `CanvasGroup` 缓存在 `物品框.组`（底座基类加 1 个字段，创建时赋值），`更新实体框` 直接取缓存 |

顺带：`摆池槽` 现在**同一格不重摆**（指纹只按"相机跨过格线"量化，一次重排里仍有大量槽显示的还是原来那一格）。

### 新增守门人：`Tools/探索接线核对.ps1`（5 段）

短路类优化最危险的**不是性能，而是"该重画时没重画"** —— 表现成"雾停在上一格/路径画的是老路线"，
**不报任何错**。所以把前提变成红灯：

1. **雾的输入写入点**（`当前可见/已探索/当前时段`）必须在例外函数里或在 `刷新视野()` 附近（窗口式判据，已写明）
2. `重建()` 必须把两个去重键重置（否则重建后那一层**永远是空的**）
3. `更新池()` 末尾必须 `刷迷雾(true)`（池槽换了格，但"版本没变"）
4. `刷路径` 必须"从终点往前分配"（倒回去就报错）
5. 三层面板不得再出现 `根.GetComponent<CanvasGroup>()`

**负向测试已做**：把四个文件 `git stash` 回优化前的版本 → **8 处报红**（§2×2 / §3 / §4×2 / §5×3）；
另外单独删掉 `大世界探索服务` 的 `刷新视野()` → §1 报 2 处；两次还原后都回到 **0 处**。

### 这一刀**没做**的结构优化（记下来，别以为漏了）

- **交互层"每格一张透明图 + 一个 `探索格点击`" → 单张交互面 + 坐标换算**：
  现在 区域层 = **704 个 GameObject + 704 个组件**，大世界池再 400 个，且池槽每次重排都要维护
  `池点击[i].列/行`（写错了就是"点到上一格"，代码里专门写了警告注释）。
  改成"一张整网格的命中面 + 指针位置 → 格坐标"能把这些全删掉，右键菜单的定位改用算出来的格矩形。
  ⚠ 代价：点击/悬停/右键路由要重测，**离线验不了**（要进 Unity 点）。
- **池槽循环索引**：现在相机每跨过一格线就把 ~400 个槽**全部**重摆；改成"槽位 = (列 mod 池列数, 行 mod 池行数)"
  之后，每次跨线只需要动**进入窗口的那一列/行**（~25 槽）。同样要重测 + 改离线脚本 `格子池区间核对`。
- **`刷迷雾` 只重画"可能变的格"**（旧/新视野方框的并集 ≈ 98 格，而不是整层 704 格）：能省 7 倍，
  但"边界算错"的后果同样是静默花屏 → 建议**先做上面的单面交互层**，再考虑这条。

> 结论（诚实版）：只从这两处 + 缓存拿到的是"每步少摆 ~30 张图 + 非视野刷新不再全层重画 + 每次刷新少 700 次组件查找"。
> **大头（区域层 704×3 张图与 704 个点击组件、大世界每跨线全池重摆）还在**，要动就是上面那三条。

### 这一刀改了两处（都**不可能改变像素**，理由写进注释）

1. **底格逐格开关 `需要底格(列,行)`**：探索层只给"地表不铺的格"（**界外**）返回 true。
   为什么像素一定不变：地表层是**不透明且逐格盖满**的（房间地板色 / 区域地面色 alpha 都是 1），
   而 `定位()` 与 `探索图层.摆格()` 用的是**同一套锚点与 pivot**（(0,1)/(0,1) + 格尺寸）→
   被地表盖住的底格一个像素也露不出来；界外格照旧保留（它是那一块唯一的地色）。
2. **拖拽开关 `需要拖拽组件`**：探索层覆写 false。理由是**可证的死代码**：
   `开始拖拽()` 第一行就是 `if (!允许开始拖拽(堆叠)) return;`，而探索层 `允许开始拖拽` 恒 false，
   所以挂在每格实体框上的 `物品拖拽` 组件**永远走不到任何一行**（Unity 的拖拽也只派发给 OnBeginDrag 的接收者，
   跨面板也不会轮到它）。区域层一次进图几百个实体框 → 省几百个 MonoBehaviour。

### 这一刀**没做**的三处（都记了数，别以为漏了）

- **格线 1462 张 → 1 张 Tiled Image**（`Image.type = Tiled` 用一格大小的线贴图平铺）：这是数量上最大的一笔。
  没做的原因：平铺的 UV 对齐可能差半像素（线的粗细/接缝会变），**是像素级风险**，
  而且它属于"看得见的东西"—— 应该由你在 Unity 里看过一眼再决定，不适合我盲改。
- **交互层 704 图 + 704 组件 → 单张交互面 + 坐标换算**：收益同样大（-1408 个对象），
  且像素完全不变（那些图是全透明的）；但它**改的是点击/悬停/右键的路由**（右键菜单靠 `格位框(列,行)` 贴格弹），
  必须点着验 —— 你说了"进 Unity 点几下验右键/悬停/雾 没有问题"，所以这条**可以接着做**。
- **逐实体脏检查**（`刷新物品()` 是"全实体遍历"，每次背包变化事件都跑一遍 700+ 个 `更新实体框`）：
  要引入每实体的签名（已搜/锁着/列/行/档），改动面比上面两条大，收益要实测（Profiler）才排得准。

## 一之八、刀22 · 修用户反馈的「路径高亮拖尾」

**现象（用户）**：路径的显示消失得比角色移动慢，看起来像拖尾。

**原因**：逻辑格要等令牌**踩到格心**才 `推进一步()`，而令牌是**连续**走过去的 ——
那 0.3 秒里"脚下那一格"其实早就离开了，但路径高亮要到踩到下一格才更新，
所以那 0.3 秒一直亮着 → 视觉上就是一条拖在角色身后的尾巴（每一步都发生一次）。

**改法（只动"哪个格子亮着"，不动逻辑）**：
`探索图层` 增加 `路径起点偏移`：刷路径 从 `路[偏移]` 开始画。
- `推进移动` 在**开段那一刻**（令牌开始走向下一格）把它置 1 → 立刻收掉刚离开那一格的高亮；
- 令牌踩到格心、逻辑格推进后归 0 → 这时 `路[0]` 正是脚下那一格，该亮的就是它。
- 偏移进签名（0→1 与 1→0 都会被认出来），所以这一次收尾是**真的重画**；
  又因为路径池是"从尾分配"，这次重画只关掉一张图，几乎免费。
- `遭遇中` / 无路 / 换世界 都归 0（换世界在 `切世界` 的重置里）。

**守门人 §4 扩容**：刷路径 必须认 `路径起点偏移`；推进移动 必须"开段置 1、踩格心归 0"。
**负向测试**（按 §六 #51 的新纪律，**手工反向编辑**注入，不用 `git checkout`）：
把偏移去掉 / 去掉"开段置 1" → §4 报 2 处；手工还原后 0。

> ⚠ 待你进 Unity 确认：点一格走一段，**高亮应跟着令牌走、身后不留亮格**；
> 顺带看一眼"脚下那一格不再亮"是否别扭（令牌自己盖着它，通常看不出来）。

## 一之十九、刀33 · 档2 #26「战斗可播种随机源」—— 然后**冻结验证工作**（用户 2026-09-13 拍板）

### 为什么先做它（它其实是游戏改动，不是测试）
战斗原来有 **8 处**直接掷随机：7 处 `UnityEngine.Random`（全局静态：不能按战斗播种，序列还会被特效/UI 搅动）
+ `战斗单位.Random()` 每次 `new System.Random()`（按时间播种 → 不可复现；同帧连建实例还会拿到相关的数）。
后果：**一场战斗无法复现**——玩家报"这场打不过/卡住"只能靠运气再碰一次；胜率也只能靠手感试（P7 调权重没有依据）。

现在：**一场战斗 = 初始状态 + 种子**。

### 做了什么
| 项 | 内容 |
|---|---|
| 新文件 | `Domain/战斗/随机源.cs` —— 唯一掷点入口。口径与 UnityEngine 对齐：`值() ∈ [0,1)`（同 `Random.value`）、`范围(a,b)` 整数**左闭右开**（同 `Random.Range(int,int)`）、`范围含(a,b)` 双闭、`b<=a` 退化返回 `a`（不抛异常） |
| 种子 | `确定性随机.派生(档案.世界种子, "战斗" + 场次)` → 同一存档、同一场次 = 同一条掷点序列。开局 `Debug.Log` 打出实际种子（报 bug 带这个数就能重放） |

## 一之二十一、刀37 · 工作台「改装」：把配件 UI 做出来（用户给的设计）

### 用户定的交互（原话）
> 「在工作台进行，将配件和武器放在材料区，点击"行动按钮"，即可将配件和武器合体。
> 反之将有配件的武器拆分出武器本体和配件。那么对于工作台，就要有2个按钮来进行功能的切换：制作、其他。」

这条比"背包里双击装配件"更好，理由有两条硬道理：
1. **主题对**：装消音器/换枪管是**工作台上的工具活**，不是站在街上随手一插；
2. **心智负担低**：双击安装得先猜"装到哪件装备的哪个槽"，而材料区把"拿什么、装什么"摆在明处。

### 实现（`UI/物品/面板/制作面板.cs`）
| 项 | 做法 |
|---|---|
| 两个模式按钮 | `制作模式按钮` / `其他模式按钮` 两个 `[SerializeField]` —— **按钮由用户在预制体里自己搭**（刀37 收口：去掉了我原先"运行时自动建按钮"的兜底，避免和你的布局打架）。本类只做三件事：挂 `onClick`、接 `音效管理器.注册按钮`、按当前模式给按钮文字上色（白=当前 / 暗淡=另一个，与「制作按钮」同一套视觉语言）。**一个都没接线 → Console 明确报该接哪两个字段**，且工作台退化成只有「制作」模式（不崩）。另暴露 `public bool 处于其他模式` 供你在预制体侧做高亮/指示 |
| 行动按钮 | **还是那一个**（用户要"一个行动按钮 + 两个模式按钮"）：`设行动按钮文字()` 按当前可执行动作改名 ——〔装配改装件〕/〔拆解配件〕 |
| 方向判定 | `改装动作()` 一处判据，刷新与点击共用：材料区 = 1 件装备 + ≥1 配件 → 装配；1 件**已带配件**的装备 → 拆解；>1 件装备 → 拒绝（"一次只改装一件"，否则不知道装到谁身上） |
| 装配 | 配件按**自己的槽**装（`配件槽.允许` 校验）；**槽已占 → 旧件也进输出区**（它同样是这次操作的产出）；**成品装备进输出区**；不匹配的配件留在材料区并提示 |
| 拆解 | **装备本体 + 拆下来的配件一起进输出区** |
| 不消耗 | 改装**不扣材料、不推时间**（与制作的区别）；demo 阶段先不加"改装耗时" |
| 收料过滤 | `当前允许材料` 在其他模式只收"有配件槽的装备 + 配件"，不再看配方 |
| 切模式 | 制作中不许切；切之前把材料区**全数返还**（旧模式的合法性判定不适用于新模式，留着会变成"东西在里面但按钮永远是灰的"）；返不回（背包满）→ 取消切换，防丢 |

### 顺手堵掉的两个坑
- **双击配件原本会走错分支**：`快捷操作` 里 `槽位 非空 → 装备选中()`，而配件的"槽位"是 `枪口/瞄具` 这类**配件槽**、不是装备槽 → 只会表现为"点了没反应"。现在明确提示「到【工作台】…」。
- **详情提示**：配件显示 `改装件〔枪口〕：到【工作台】…（适配 N 类装备）`；能改装的装备追加 `可在【工作台】改装（槽位 枪口/瞄具/…）`（同一份 `配件槽.装备可用` 口径）。

### ★ 输出区语义（用户 2026-09-13 纠正后改的）
原实现把"结果"留在材料区（装配完武器还在材料区、拆下的配件塞回材料区）—— 用户指出：
> 「拆除后的，合成后的，要输出到输出网格里啊。」

改成与**制作**同一套语义：**材料区 = 输入，输出区 = 结果**。
- 装配：成品装备（带新配件）→ 输出区；被换下的旧配件 → 输出区
- 拆解：装备本体 → 输出区；拆下来的每个配件 → 输出区
- **放不下就整体回滚**：装备原样回材料区、配件表不动、待装配件不消耗（三步式：先算 → 再放 → 最后提交配件表）。
  这比"能放几件算几件"更安全：玩家不会拿到一个"装了一半"的装备，也不会凭空少东西。
- 提示文案同步（详情里写明"结果出现在【输出区】"）。

### ⚠ 待你在 Unity 里确认（离线测不了）
1. 两个模式按钮由你在预制体里搭：加两个 `Button`，把组件拖到 `制作模式按钮` / `其他模式按钮` 字段上即可（**不要**在预制体上另加 onClick）；按钮文字色由代码按模式切换，若你做了自己的高亮就忽略它。
2. 拖拽：材料区（`制作输入网格`）现在按模式只收合法物品；把"已装备的武器"拖进材料区是否顺手（装备需要先脱下，或直接从装具块拖），要你试一下手感。
3. 装配后关闭面板 → 武器带着配件回背包 → 再装备 → 副属性是否真的生效（`装备管理器.副属性` 这条链**离线只能证明编译过**）。

我的搬运代码是 `输入会话.网格物品.Remove(目标)` → `输出会话.放入网格堆叠(目标)`。
**从旧列表移除后，堆叠的 `列/行` 仍是旧网格里的坐标（≥0）** → `放入网格堆叠` 直接 `return true`、**什么都没做**，
而它已经从输入列表里被摘掉了 → 这件东西**两个列表都不在** = 玩家看到"装备本体没了"（实际是被悬空了）。
**修法**：所有会话间搬运走两个新helper `移出会话` / `放入会话` —— 搬之前把 `列/行` 复位成 `-1`
（与 `返还会话物品` 里那句 `堆叠.列 = -1; 堆叠.行 = -1;` 是同一条纪律，我这次漏了）。
回滚路径同样走它们（否则回滚也会把装备悬空）。

### ② 拆出来的配件显示"损坏" —— 两处叠加
- **直接原因**：`物品网格面板.渲染` 的耐久角标条件是 `当前耐久 <= 0 → 显示"损坏"`（在 `耐久上限 > 0` 时），
  而我 `new 物品堆叠(标识, 1)` 时**没有初始化 `当前耐久`**（默认 0）→ 0/上限 = 损坏。
  仓库/搜索/掉落 都有初始化（`当前耐久 = 有效最大耐久(标识)`）—— 我又漏了一条既有约定。
  修法：新增 `新堆叠(标识, 数量)` helper（按同一约定初始化），拆解/装配换下来的旧件都走它。
- **根因（设计层）**：`装备管理器.有效最大耐久` 有一条兜底 —— "有攻击或防御加成的装备默认 15"，
  而 **陶瓷插板 防御加成 +6、JSON 里没写 最大耐久** → 被当成"有耐久的装备"。
  配件根本不该吃武器/防具的这条兜底。修法：`有效最大耐久` 增加一句
  `if (物品类型解析(标识) == "配件") return 配;`（配件只有显式配了 最大耐久 才有耐久）——
  新增 `玩家档案.物品类型解析` + PlayerService 接线（同 `配件加成解析` 的路子）。
  这样"配件忘初始化就显示损坏"这一整类问题从根上没了。

### ③ 配件能被"装备" —— 判据只看了"槽位非空"
配件有 `槽位`（枪口/瞄具/插板… 那是**配件槽**），于是：
- `右键菜单.显示` 的 `槽位 非空 → 加「装备」条目` 会给配件一个「装备」，点了必然失败；
- 真点了还会走到 `面板操作.换装堆叠(槽="枪口")` —— 拿配件槽去当装备槽。
**修法**：判据改成「槽位非空 **且** `配件槽.认得出(槽位) == false`」（排除配件槽）；
并在**两个**装备入口（`换装堆叠` 实例级 + `换装` 模板级）各加一道拦截 + 明确提示
"到【工作台】「其他」里改装"。拦在 `换装堆叠` 是因为它是**双击/右键/拖拽三个入口的共同落点** ——
一处拦住，三个入口全兜住（比在每个入口各判一次可靠）。

### 验证
编译 exit 0；分层核对 / 目录核对 / 文档核对 / 战斗接线核对 全绿；战斗验证 122 断言 0 失败。
**仍需你复测**：工作台上 装配 → 看输出区有成品；拆解 → 输出区有本体 + 配件（且不显示"损坏"）；
背包里右键配件 → **没有**「装备」条目；双击配件 → 提示到工作台。

### 三条教训（值得记）
1. **既有约定是防线**：`放入网格堆叠` 前复位 `列/行`、建堆叠初始化 `当前耐久` —— 两条我都是"漏了"而不是"不知道"，说明**约定得写进注释/检查**，光在心里记不住。
2. **兜底规则会漏到不该管的地方**：`有效最大耐久` 的 15 兜底本意是武器/防具，结果配件也跟着吃 → 加类型判断把它圈回范围。
3. **"槽位非空"不等于"是装备"**：一个字段被两类东西共用（装备槽 vs 配件槽）时，判据必须能区分二者。
